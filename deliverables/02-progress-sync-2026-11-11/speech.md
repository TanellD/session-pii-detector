## Слайд 1. Из каких частей собираем сервис

Начнём с частей сервиса, чтобы дальше было понятно, где применяются метрики. На входе новое сообщение и идентификатор сессии. Regex и NER извлекают упоминания с типами и границами. Нормализация устраняет конфликты и повторы. Линковка определяет, какому человеку принадлежат атрибуты, и явно сохраняет неизвестную принадлежность. Затем обновляется состояние по людям, а политика формирует скор и первый алерт. Нормализация и линковка согласуются между собой: окончательный повтор разрешается с учётом владельца. Это рабочая схема для MVP. Извлечение уже проверялось на CPU; сессионное ядро ещё предстоит собрать. Историю повторно через NER не пропускаем. Явно общий факт может принадлежать разным людям; родство само по себе не доказывает общие атрибуты.

## Слайд 2. Как проверяем каждый компонент

Теперь распределим измерения по компонентам. Для извлечения считаем точное совпадение границ и типа: TP — найденный эталонный спан, FP — лишний, FN — пропущенный. Используем Precision, Recall и F2 с большим весом полноты. Для линковки сначала подаём эталонные атрибуты: это отделяет ошибки владельца от ошибок NER. Pairwise проверяет, есть ли у пары атрибутов общий известный владелец. Лишнее объединение даёт FP, разделение — FN; считаем Precision, Recall и F1 по парам. B-cubed остаётся альтернативной диагностикой на однозначном срезе: P_m=|C(m)∩G(m)|/|C(m)|, R_m=|C(m)∩G(m)|/|G(m)|; затем средние по элементам и F1=2PR/(P+R). Общие владельцы требуют адаптации. Весь сервис измеряем по задержке от принятия полного сообщения обработчиком до готового ответа после обновления состояния. Сеть клиента, очередь до обработчика и внешняя LLM не входят в эту границу. Публикуем квантили, ошибки, нагрузку и рост памяти. Численного бюджета пока нет.

## Слайд 3. Главное — первый алерт вовремя

Основная итоговая метрика — F2-timely. t_gold — первое сообщение, на котором по эталонной политике требуется алерт; t_pred — сообщение первого алерта системы. Точное попадание — TP. Ранний алерт — FP. Опоздание или отсутствие алерта — FN. На отрицательной сессии любой алерт — FP. Для F2-session используем ту же формулу, но другие счётчики: любой алерт в положительной сессии даёт TP независимо от позиции. Это диагностика наличия распознавания. Offset считаем только там, где есть и эталонный, и предсказанный момент, то есть на TP-session. Отрицательный offset — рано, положительный — поздно. FP0 — доля отрицательных сессий с ложным алертом. Все основные счётчики суммируем по корпусу, затем вычисляем метрики. Важное ограничение: Recall-timely не включает ранние алерты в знаменатель и не является долей точных попаданий среди всех положительных сессий. Неуверенный эталон исключается с отдельным отчётом; это не разрешение исключать неудобные предсказания системы. Пустые знаменатели — N/A. Численных результатов baseline ещё нет.
