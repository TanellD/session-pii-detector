# Сборка сессионного сервиса и подключение компонентов

В ветке feat/docker-service-v2 добавлен [runtime v2](docker-service-v2.md):
стандартный Compose включает адаптер v2 и явный bypass линкера для замеров,
отдельный модельный образ, readiness и структурированные тайминги. Описание
ниже сохраняет исходный каркас; для новых настроек использовать страницу v2.

Рабочий каркас HTTP-сервиса находится в `src/session_pii/`. API имеет идентификатор `service-scaffold-v1`. Старый [draft v0.1](session-api.md) остаётся историческим предложением; его схемы не описывают этот запуск.

Сейчас API, состояние сессии и обработчик правил подключены к адаптеру Олеси. По умолчанию выполняется его regex-часть; GLiNER включается явно для локально подготовленных весов. Линкер по умолчанию остаётся заглушкой. `session_alert=false` при `coverage_complete=false` нельзя использовать как разрешение пропустить сообщение без проверки.

## Запуск Docker

Из корня репозитория при работающем Docker Engine:

```powershell
docker compose up --build
```

Если установлен только отдельный Compose: `docker-compose up --build`.

- API: `http://127.0.0.1:8000`.
- Swagger UI: `http://127.0.0.1:8000/docs`.
- OpenAPI JSON: `http://127.0.0.1:8000/openapi.json`.
- Проверка живого процесса: `GET /healthz`. Она не означает готовность NER.

Порт на хосте можно изменить переменной `PII_HOST_PORT` (по умолчанию 8000), например в PowerShell: `$env:PII_HOST_PORT='8018'`, затем та же команда Compose.

Без Compose:

```powershell
docker build -t session-pii:scaffold .
docker run --rm --name session-pii -p 127.0.0.1:8000:8000 session-pii:scaffold
```

`.dockerignore` допускает в контекст только нужный код, конфиг и фиксированные зависимости. `.env`, данные, веса и результаты экспериментов в образ не попадают. Контейнер работает под UID 10001; Compose дополнительно включает файловую систему только для чтения. Ключи для regex-режима не нужны. Базовый образ не содержит GLiNER и весов.

```powershell
python -m venv .venv-service
.venv-service\Scripts\python.exe -m pip install -r requirements-service-test.txt
.venv-service\Scripts\python.exe -m uvicorn session_pii.app:app --app-dir src --host 127.0.0.1 --port 8000 --workers 1 --no-access-log
```

В другом терминале:

```powershell
.venv-service\Scripts\python.exe -X utf8 tools/smoke_service.py
.venv-service\Scripts\python.exe -X utf8 -m unittest discover -s tests/service -v
```

На Linux замените `.venv-service\Scripts\python.exe` на `.venv-service/bin/python`. Запускайте из корня репозитория: сервис использует валидатор из `tools/` и конфиг `configs/runtime-risk-policy.json`. Сервисные тесты находятся отдельно от исследовательских тестов и требуют зависимостей FastAPI.

## Один запрос по шагам

```powershell
$piiSession = Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/v1/sessions -ContentType application/json -Body '{"session_id":"synthetic-demo"}'
$piiBody = @{
    session_id = $piiSession.session_id
    session_epoch = $piiSession.session_epoch
    expected_state_version = 0
    message = @{ message_id = 1; role = 'user'; text = 'Как отключить уведомления?' }
} | ConvertTo-Json -Depth 5
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/v1/analyze -ContentType application/json -Body ([System.Text.Encoding]::UTF8.GetBytes($piiBody))
```

В режиме `PII_DETECTOR_MODE=stub` ответ содержит пустые `entities`, `state_version=1`, `coverage_complete=false` и причины `ner_not_configured`, `regexp_not_configured`, `linker_not_configured`. По умолчанию regex извлекает доступные классы; причины неполноты — `ner_not_configured` и `linker_not_configured`. Недоступный компонент не маскируется под отсутствие сущностей в полностью проверенном тексте и не включает статистическую неуверенность автоматически.

| Метод и путь | Назначение |
|---|---|
| `POST /v1/sessions` | Явно создать сессию и получить новый `session_epoch`. |
| `POST /v1/analyze` | Принять ровно одно новое пользовательское сообщение. |
| `GET /v1/sessions/{session_id}` | Прочитать версию, вердикт и неизменяемые пометки прошлых сообщений. |
| `POST /v1/sessions/{session_id}/reset` | Проверить epoch/version и явно начать новый epoch с пустым состоянием. |

`message_id` начинается с 1 и увеличивается без пропусков; `expected_state_version` берётся из последнего ответа. Точный повтор последнего запроса возвращает тот же результат без повторного NER. Изменённый или старый запрос получает 409; состояние в ошибке помогает восстановить порядок. После истечения TTL analyze получает 410; нужна явная операция create. GET не продлевает TTL.

`session_id` — строка длиной до 128 символов: латинские буквы, цифры, `_` и `-`. UUID без фигурных скобок подходит. Поля запроса проверяются строго; новые произвольные поля не принимаются.

При ошибке компонента — 502, при превышении лимитов сообщений/сущностей — 413. Сообщение не принимается, версия и прежние факты не меняются. Ошибки схемы — 422 без отражения входного текста. Поддерживается только `role=user`; фильтрация assistant/tool выполняется вызывающей стороной. Batch и предыдущий ответ чатбота в этот контракт не входят.

## Куда вставлять NER, regexp и линкер

Точки подключения — `src/session_pii/components.py`. Выберите свои объекты в `create_app()` файла `src/session_pii/app.py` или передайте их фабрике:

```python
app = create_app(ner=MyNER(), regexp=MyRegexp(), linker=MyLinker())
```

NER и regexp реализуют `detect(message) -> DetectionResult`. Вход — только новое сообщение. Выход — кортеж `Span(type, start, end, score)`; значения типов берутся из `models.py`. Позиции — Unicode code points `[start,end)` исходной строки, без предварительного удаления пробелов. Для regexp `score=None`; оценки разных моделей не усредняются. `fio`/`PERSON` не принимаются: адаптер должен выдать отдельные `first_name`, `last_name`, `patronymic` по [ТЗ](../data/annotation-guidelines.md).

Полноценно работающий компонент возвращает `complete=True`, в том числе когда сущностей нет. Заглушка/частичный анализ — `complete=False` и короткие машинные коды `reasons`, без исходных текстов и персональных значений. Исключения прерывают принятие сообщения; их текст не отправляется клиенту. Таймаут вызова внешней модели должен реализовать её адаптер.

Точные дубли `(start,end,type)` объединяются с сохранением источников. Любое другое перекрытие сейчас отклоняется целиком: перед подключением детекторов нужно согласовать разрешение таких конфликтов либо добавить его отдельным этапом. Несовпадающие типы не выбираются по несопоставимым score.

Линкер реализует `link(message, candidates, known_facts) -> LinkResult`. `person_ids` содержит одну запись на каждый новый Candidate в исходном порядке: одного владельца, tuple совместных владельцев либо `None`. Известный `person_id` можно повторно использовать; новый ID создаётся внутри данного epoch; `None` означает неизвестного владельца/служебный контакт и не объединяет такие сущности в человека. Линкер видит неизменяемые факты с происхождением, а не полные тексты прежних сообщений. Он не может переписать прежние спаны и их владельцев. `None` сам по себе не делает линковку неполной: если решение об неизвестном владельце принято, допустим `complete=True`.

Для явно служебного телефона/email линкер дополнительно выставляет `service_contacts`: булеву маску по всем кандидатам в том же порядке. Такие контакты остаются с `person_id=None`, сохраняются как сущности, но не участвуют в сумме. Пустая маска означает отсутствие явно служебных контактов. Нельзя помечать этим флагом красную сущность или сущность с известной персоной. Неизвестная принадлежность и подтверждённый служебный контакт имеют разный смысл.

Объекты компонентов общие для всех сессий процесса и должны допускать вызовы из разных потоков либо иметь собственную синхронизацию. Для одной сессии обработка сериализована.

## Правила и состояние

Путь обработки: новое сообщение → NER + regexp → проверка спанов и удаление дублей → линкер → накопленные факты по людям → `RiskEvaluator` → вердикт. После каждого сообщения проверяются **все люди в истории**, даже если в новом сообщении они не упомянуты. Детекторы при этом не перечитывают историю. Пересчёт только изменённых людей возможен позднее при сохранении оценок остальных и отдельном обновлении неизвестных фактов.

Конфиг `configs/runtime-risk-policy.json` задаёт отдельную политику `runtime-risk-v2`. Веса — согласованные настройки сервиса, не вероятности и не статистическая оценка количества людей:

| Группа | Типы | Вес |
|---|---|---:|
| Жёлтая | Отдельные Ф, И, О; пол, возраст, география, профессия, организация | 0,1 |
| Оранжевая | Телефон, email, полный адрес; производные ФИ, ИО, ФО, ФИО | 0,3 |
| Красная | Паспорт, СНИЛС, ИНН физлица, банковская карта | 1,0 |

Для человека суммируется один вес каждого активного типа. Повтор email или исправление значения того же типа не увеличивает сумму. Исторические упоминания остаются в состоянии. Части имени собираются обработчиком: ФИ/ИО/ФО/ФИО получают один вес 0,3 вместо суммы частей. У разных людей суммы раздельные; confidence в `Span.score` на сумму риска не влияет.

Проверки по человеку:

1. Красная сущность — `red_rule` независимо от суммы.
2. Согласованные сочетания — `combination_rule`: ФИ/ИО/ФО/ФИО + личный телефон, email или полный адрес; личный телефон + email. Организация остаётся жёлтой. Произвольная пара оранжевых не создаёт это правило.
3. Сумма строго больше `person_threshold=0.5` — `score_rule`. Ровно 0,5 не даёт алерт.

У неизвестных фактов отдельная сумма и `unknown_threshold=0.5`. Они не считаются одним человеком, части имени не собираются в ФИО. Точные повторы `(тип, написание без внешних пробелов и с приведённым регистром)` дают один вклад; разные значения одного типа дают отдельные вклады. Здесь действуют **только красное правило и сумма**, без сочетаний. Поэтому неизвестные телефон + email при текущих весах всё равно дают алерт по сумме 0,6. Для сравнения повторов цифровые идентификаторы приводятся к цифрам, а начальная 8 российского телефона — к 7. Исходные значения и границы сохраняются. Явно служебные контакты исключены из суммы.

Ответ содержит `person_risks` по ID людей и отдельный `unknown_risk`: `risk_score`, `threshold`, `rules`, `missing_weights`. При нескольких причинах приоритет первой причины: красное → сочетание → сумма. Отсутствующий вес не подменяется нулём: сумма соответствующей группы `null`, `coverage_complete=false`, причина `risk_weights_not_configured`; независимые красные правила и сочетания продолжают работать. По умолчанию все веса заданы. Конфиг читается при создании приложения; после изменения нужен перезапуск и новые сессии.

`current_alert` объединяет результаты текущей проверки людей и неизвестных фактов. `session_alert` и `first_alert_message_id` сохраняют первое историческое срабатывание до reset. История сообщений не переписывается. Полнота выполнения компонентов выражена отдельно в `coverage_complete`; её потеря сохраняется до reset.

**Статистический калькулятор и эталон разметки пока используют отдельную политику.** Оценка круга лиц ≤100 не является суммарным риском и в этом runtime не запускается. `candidate_counts` оставлено пустым для совместимости контракта. Статистические средние, адресное обогащение и национальные частоты в скор не переводятся. `annotation_uncertain` при оценке только по весам не устанавливается из-за отсутствия статистики; прежняя историческая пометка сохраняется, если она была в переданном состоянии. Эталонные алерты назначаются независимо по ТЗ. Для оценки используйте новую согласованную версию разметки; веса и пороги подбираются на обучающей/настроечной части, итоговое качество — на отложенной. Не создавайте эталон из текущих весов сервиса. ТЗ разметки и сохранённые метки этим изменением не переписаны.

Факты со значениями хранятся только в памяти. Полные исходные сообщения не сохраняются; для точного retry остаются хеш запроса и последний ответ. Перезапуск процесса теряет всё состояние: старый analyze получает 410, а продолжение начинается только с нового create. До подключения общего хранилища используйте один процесс Uvicorn и одну реплику. Проверка аутентификации и промышленный gateway в каркас не входят; опубликованный Compose-порт ограничен localhost.

Очистка истёкших записей выполняется при создании сессий; отдельного фонового таймера физического удаления из памяти пока нет. TTL запрещает чтение и продолжение истёкшего epoch независимо от времени очистки. Для постоянной эксплуатации нужен явный выбор хранилища и политики удаления.

| Переменная | Начальное значение | Смысл |
|---|---:|---|
| `PII_TTL_SECONDS` | 1800 | Неактивность до истечения epoch. |
| `PII_MAX_SESSIONS` | 1000 | Число активных сессий процесса. |
| `PII_MAX_MESSAGES` | 1000 | Число принятых сообщений на epoch. |
| `PII_MAX_ENTITIES` | 1000 | Число сохранённых упоминаний на epoch, включая повторы. |

Это изменяемые эксплуатационные ограничения каркаса. Веса и пороги риска задаёт отдельный конфиг `runtime-risk-policy.json`.

При добавлении GPU-модели допишите её зависимости в отдельное окружение и Docker-сборку. Веса подключайте отдельно; не добавляйте `data/` и `.env` в COPY. После подключения компонентов выполните интеграционные проверки и отдельный замер качества/скорости на размеченных сессиях.

В `.github/workflows/ci.yml` добавлена проверка сервиса: интеграционные тесты, Docker-сборка, ожидание healthcheck, HTTP smoke и остановка тестового Compose-проекта.

Основа контейнерного запуска и тестового клиента: [официальная документация FastAPI по Docker](https://fastapi.tiangolo.com/deployment/docker/), [тестированию](https://fastapi.tiangolo.com/tutorial/testing/).

## Несколько владельцев атрибута

Расширение `ownership-v2` сохраняет прежние строковый `person_id` и `null`; JSON-ответ также допускает список ID. `LinkResult.person_ids` содержит одну запись на кандидата: строку, tuple разных ID или `None`. В HTTP JSON tuple сериализуется списком. Один общий атрибут хранится одним `Entity` и одним `Fact`, но участвует в риске каждого явно указанного владельца. Неизвестный риск его не включает; люди и их остальные атрибуты не объединяются. Пустые наборы, повторяющиеся и пустые ID отвергаются до изменения состояния. Служебный контакт может иметь только неизвестную принадлежность. Стандартная заглушка линкера по-прежнему возвращает `None`; автоматическое распознавание совместных владельцев требует реального линкера.

## Режим извлечения и подключение модели

Линкер выбирается отдельно через `PII_LINKER_MODE=stub|random|gemma`.
Для Gemma нужен `RADEON_API_KEY`; контракт, ограниченный контекст внутри
сессии и запуск описаны в [инструкции baseline](gemma-linker-baseline.md).

`PII_DETECTOR_MODE=regex` — начальный режим без дополнительных модельных зависимостей. `AdapterDetector` вызывает `benchmarks.adapter.adapter.extract()` один раз на новое сообщение; вторая стадия `EmptyDetector` не запускает regex повторно. Контекстные части имени также доступны без модели. `stub` сохраняет прежний пустой каркас.

Для `gliner` подготовьте модель по инструкции benchmarks/pii_smoke/README.md в отдельном окружении с GLiNER и зависимостями сервиса, затем задайте PII_MODEL_DIR. Пример локального запуска:

Практическая установка на Windows с Python 3.11, исправление Unicode-пути tokenizer
и результаты реального запуска описаны в [эксперименте GLiNER](../experiments/2026-11-24-gliner-runtime-250.md).

```powershell
$env:PII_DETECTOR_MODE='gliner'
$env:PII_MODEL_DIR='outputs/task12-prepared-model'
python -m uvicorn session_pii.app:app --app-dir src --host 127.0.0.1 --port 8000 --workers 1 --no-access-log
```

Проверяется manifest.json, версии модели/backbone и хеши подготовленных файлов; загрузка выполняется только из локального каталога с local_files_only=True. Ошибка модели даёт 502 без изменения сессии, без молчаливого перехода к regex и без раскрытия текста ошибки. Веса не скачиваются приложением. Необязательный russiannames не включён в базовый образ; работает согласованный fallback адаптера. Качество реальной GLiNER данным интеграционным изменением не подтверждено.

## Происхождение, ID и пересечения

Каждый возвращённый адаптером Mention преобразуется в Span с provenance: локальный mention_id, источник, версия детектора, исходный confidence и его вид. Confidence не используется как вес риска. При дедупликации одинаковых кандидатов источники сохраняются, несовместимые оценки не усредняются.

Entity.mention_keys задаёт составной ключ `(session_id, session_epoch, message_id, mention_id)`. Он различает одинаковые локальные ID в разных сообщениях, сессиях и после reset. Entity.id остаётся локальным ID сервисного спана в сообщении. Fact сохраняет происхождение и ссылки для линкера. Эта уникальность не заменяет дедупликацию смысловых фактов.

Перед линковкой обработчик разрешает согласованные пересечения: документ подавляет PHONE на тех же цифрах; организация подавляет вложенные части имени и PERSON; полный адрес подавляет вложенную географию; контакт подавляет вложенный PERSON; типизированная часть имени подавляет покрывающий PERSON. Ответ suppressed содержит границы, типы и причину исключения, без копии исходного текста. Неопределённый конфликт разных типов не разрешается сравнением confidence: запрос отклоняется с 502, состояние сохраняется.

`person` имеет жёлтый вес 0.1 и участвует в сумме, но не создаёт ФИ/ИО/ФО/ФИО. Точные повторы не добавляют вес. Если у того же владельца позднее выделены части, покрывающие то же значение PERSON, общий сигнал не учитывается повторно. Люди не объединяются по совпавшему тексту имени. Совместный атрибут учитывается отдельно у каждого явно известного владельца.

Проверка живого HTTP с regex и красным синтетическим документом: python -X utf8 tools/smoke_service.py --expect-adapter. Отсутствующий настоящий линкер остаётся явным ограничением, даже если извлечение работает.
