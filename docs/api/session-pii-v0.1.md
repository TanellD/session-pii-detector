# Контракт сервиса v0.1 — предложение для #12

Статус: **draft**, 02.11.2026, `Kopylov-Andrey`. Сервис не реализован.
Это каркас для обсуждения, не утверждённый контракт HiveTrace.
[Схемы](session-pii.schema.json), [примеры](session-pii-examples.json),
[ADR](../decisions/0003-detector-independent-session-layer.md).

## Основания и границы

Ментор подтвердил `session_id`, вердикт сообщения и сессии, момент срабатывания,
инкрементальный анализ без NER истории. Пример внутреннего NER API не получен.
За образец взяты Presidio (`entity_type/start/end/score`, T12-03) и Amazon
Comprehend (`Type/BeginOffset/EndOffset/Score`, T12-06), ссылки в реестре источников.
Адаптер меняет названия полей, не смысл уверенности.

Предложение PR #16 включает уровни и факты по людям. Оно используется как
отправная точка, но правила и роли остаются несогласованными. Авторизация,
деплой и production-нагрузка не входят в этот контракт исследования.

## Запрос

Предлагаемый endpoint: `POST /v1/analyze`. JSON содержит `session_id` и ровно
одно из `message` / `messages`. Одиночное сообщение эквивалентно batch из него.
Поля сообщения: `message_id`, `role`, `text`; необязательный
`previous_assistant_message` — контекст, не доказательство фактов о человеке.

```json
{"session_id":"s-example","message":{"message_id":1,"role":"user","text":"Мой телефон +7 000 000-00-01."}}
```

Полные пары request/response — в JSON-примерах. Они иллюстрируют предложенную
политику `draft-two-orange-v1`, не являются измеренным выходом GLiNER.

## Ответ

`results` содержит результат после каждого нового сообщения в порядке входа,
включая промежуточные состояния batch. `entities` относится к текущему тексту.
`message_verdict` оценивает только факты текущего сообщения; `session_verdict`
использует накопленное состояние. Поэтому сообщение с одним email может иметь
`no_alert`, а сессия после него — `alert` благодаря ранее названному телефону.

- `start/end`: полуинтервал Unicode code points `[start,end)` исходного текста,
  до нормализации. Не байты и не UTF-16 code units; JavaScript-клиенту нужен
  явный пересчёт, особенно при emoji. `text[start:end]` возвращает фрагмент в Python.
- `score`: непреобразованный score модели; это не вероятность ПДн или нарушения.
  Для regex — `null`, `score_kind=deterministic`. Score разных моделей напрямую
  не сравнивается. Успех checksum не приравнивается к уверенности `1.0`.
- `person_id`: локальный непрозрачный ID в пределах `session_epoch`; `null`, если
  принадлежность не установлена. Детектор сам его не создаёт, это результат линковки.
- `risk_score`: отдельное неотрицательное число либо `null`; шкала и порог
  задаются `policy_version`, не обязаны лежать в `[0,1]`. До решения #11 — `null`.
- `rule`: причина алерта `red_marker/two_orange/score`; при отсутствии правила `null`.
- `markers`: ссылки на исходное сообщение и фрагмент, поддерживающий решение;
  сырые тексты истории целиком в ответ не возвращаются.
- `first_violation_message_id`: историческое первое достижение порога за epoch.
  Название сохранено для связи с постановкой; это **техническое срабатывание
  политики, а не юридическое заключение о нарушении ФЗ-152**.

Уровни: `no_alert` — порог не достигнут; `warning` — ранний риск по отдельно
согласуемому правилу; `alert` — достигнут порог; `unknown` — надёжно оценить нельзя.
`no_alert` не означает доказанную безопасность. `coverage_complete=false` обязателен
при пропущенной области анализа, лимите состояния или неразрешённой атрибуции.
Причина отражается в `reason`. Если уже есть доказанный алерт, `decision=alert`
сохраняется даже при неполном дальнейшем покрытии; иначе используем `unknown`.

## Порядок, batch и повторная отправка

Предлагаемые правила, требующие подтверждения команды:

1. `message_id` — последовательный целый номер, начинается с единицы внутри epoch.
   Требуются непрерывность и строгий порядок; сервер не сортирует и не угадывает историю.
2. Один запрос относится к одной сессии. Batch обрабатывается последовательно и
   атомарно: при ошибке валидности/детектора состояние не меняется. NER вызывается
   только для новых сообщений, а не для ранее обработанной истории.
3. Новый запрос после первого передаёт `session_epoch` и `expected_state_version`.
   Версия увеличивается на число принятых сообщений. Несовпадение — HTTP 409.
   Изменения одной сессии сериализуются, между сессиями состояние не смешивается.
4. Точный повтор последнего запроса (IDs, роли, тексты, контекст и версия совпадают)
   возвращает сохранённый ответ без NER и без изменения состояния. Проверка повтора
   выполняется до проверки старой expected version. Повтор с другим содержимым — 409.
5. Для MVP хранится квитанция только последнего запроса. Старый retry либо
   смешанный batch из старых и новых сообщений — 409, клиент должен сверить состояние.
   Это ограничивает память. Долгая история квитанций не обещается.

## Состояние и исправления

Состояние принадлежит сервису: факты и их происхождение по людям, индексы,
исторический первый алерт, версия политики и квитанция. Хранение сырой истории
по умолчанию не требуется. Повторы одного нормализованного факта не увеличивают
риск повторно; телефон, найденный regex и моделью, — один факт.

Отрицание и исправление не превращаются автоматически в добавление нового
положительного факта. Предложение MVP: помечать прежний факт отозванным после
уверенного исправления и отдельно пересчитывать текущее состояние человека;
исторический первый алерт остаётся. Неуверенное исправление оставляет покрытие
неполным. Конкретная линковка и truth/retraction — работа этапа MVP, не доказана
нашим smoke-прогоном NER.

TTL, предел числа людей/фактов и правила удаления должны быть конфигурацией.
Численные лимиты пока не утверждены. Превышение лимита не маскируется под `no_alert`:
возвращается неполное покрытие с причиной, далее требуется сброс или другая политика.
При истечении TTL продолжение старого epoch получает 410 `SESSION_EXPIRED`.
Сбрасываем явно через предлагаемый `DELETE /v1/sessions/{session_id}?epoch=...`;
новый epoch начинается с ID=1. Исчезновение состояния не должно быть незаметным.
Семантика reset описана; отдельная HTTP-схема endpoint будет в реализации MVP.

## Роли

В предлагаемом MVP извлекаем факты только из `user`. `assistant/tool` допускаются
форматом, но возвращают `analysis_status=not_in_scope`, без сущностей; их текст
не накапливается как раскрытие пользователя. Покрытие сессии отмечается неполным,
если от этих ролей ожидается содержательный анализ. Поддержка harness и предыдущего
ответа бота требует решения #11/ментора. Это не обещание уже реализованной функции.

## Ошибки и неизменность состояния

| HTTP | code | Смысл |
|---|---|---|
| 422 | INVALID_REQUEST | Неверная схема, оба message/messages, пустой batch, повтор ID внутри batch |
| 409 | OUT_OF_ORDER | Пропуск номера, старая история вне последней квитанции |
| 409 | MESSAGE_CONFLICT | Изменённое содержимое уже принятого ID |
| 409 | STATE_CONFLICT | Epoch / версия состояния не совпадают |
| 410 | SESSION_EXPIRED | Состояние старого epoch удалено |
| 503 | DETECTOR_UNAVAILABLE | Детектор не завершил обработку; ничего не закоммичено |

JSON Schema проверяет форму; порядок, транзакции, TTL и конкурентность — требования
к будущей реализации, они не доказываются валидацией JSON-примеров.
