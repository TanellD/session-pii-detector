# Общий конфиг обработчика и LLM-разметчика

Конфиг определяет рабочие правила обработчика и контекст LLM-разметчика.

## Принадлежность и вердикт

- `entity.person_id=null` — принадлежность неизвестна или связь с человеком не установлена. Это не самостоятельная причина неопределённости вердикта; такие сущности не объединяются в одну неизвестную персону.
- Служебные контакты сохраняются без персоны и не дают личного основания алерта.
- `case_flags.annotation_uncertain=true` — в исходной разметке или истории есть пометка для уточнения ТЗ/статистики. Неуверенность не является алертом. Поздние данные не снимают ранние пометки; кейсовый флаг может сочетаться с поздним алертом. Без пометок — `false` и причина `null`.
- «Мой телефон», «моя почта», «я живу…» — явная принадлежность говорящему, разрешённая без местоименной кореференции. «Он», «его» и родственные цепочки по-прежнему не разрешаются автоматически.

Схема спана не расширена. Старое значение причины `person_attribution` читается для совместимости, но не назначается из-за одного `person_id=null`. Входная аннотация и её флаги сохраняются; обработчик добавляет пометки каждого префикса, не стирая прежние. Бинарные метрики используют факт алерта, а не флаг уточнения.

## Конфиг — единый источник правил

Используется существующий `configs/annotation-estimator-policy.json`. Обработчик читает этот файл, а `tools/export_annotation_context.py` формирует из него контекст `annotation-context-v1`. В нём есть порог, правила сочетаний, источники/даты принятых оценок и статус доступности расчётов. Подготовленные средние размеров населённых пунктов и неизвестного МКД ещё не подключены к оценщику. Среднее работодателя и средние занятой квартиры/индивидуального дома активны и находятся непосредственно в конфиге (`employer_size`, `housing_defaults`). Для МКД с известным числом квартир применяется число квартир × средняя заселённость квартиры. [Оценка по строке адреса](address-population-estimator.md) описывает автоматический поиск и ограничения.

```powershell
python -X utf8 tools/export_annotation_context.py --output data/reference/annotation-llm-context.json
python -X utf8 -m unittest discover -s tests -p test_annotation_contract.py
python -X utf8 -m unittest discover -s tests -p test_llm_annotation_pilot.py
```

Экспорт не читает секреты и персональные частотные записи. `tools/run_llm_annotation_pilot.py` прикладывает контекст к инструкции автоматически и сохраняет хеш политики в манифесте. Инструкция, точные исходные сообщения, модель и конфиг должны фиксироваться для каждого отдельного запуска. Экспортировать целиком переписные таблицы в каждый промпт не требуется.

## Сейчас — контекст в промпте

Для небольшого пилота достаточно приложить краткую инструкцию и JSON-контекст. LLM выделяет сущности, выбирает персоны и замечает пробелы ТЗ; детерминированный обработчик рассчитывает основания алерта и итоговую достаточность статистики. LLM не должна вручную воспроизводить арифметику справочников или придумывать частоты. JSON Schema ответа ограничивает структуру, но сама по себе не выполняет численные правила.

## MCP — возможный следующий интерфейс

При появлении большого справочника полезны операции чтения контекста, поиска адреса и вызова оценщика. MCP пока не реализован. Операционный результат — алерт либо отсутствие алерта, отдельно пометка для уточнения, оценка кандидатов при наличии, источники/даты/допущения и версия политики. Внутреннее отсутствие численной оценки не заменяется нулём.

MCP и контекст промпта должны обращаться к одному конфигу и одному оценщику. Они являются способами доступа, а не двумя реализациями статистических правил. Выбор MCP не исправляет отсутствующую статистику или ещё не подключённый коэффициент.
