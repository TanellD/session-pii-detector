## Определение и классы
1. Мы считаем, что сессия становится ПДн в том сообщении, после которого про кого-то — самого пользователя или человека, о котором он пишет, — набирается достаточно, чтобы понять, кто это. Такое определение подходит?
2. Классы для MVP разбили на три группы:
   - сразу алерт — паспорт, СНИЛС, ИНН, номер карты;
   - сильные — телефон, email, ФИО полностью, точный адрес; два таких про одного человека — алерт;
   - слабые, копятся по человеку — имя или фамилия, пол, возраст, город, работа, родство.

   Плюс отдельная отметка для здоровья, религии и т.п. Что-то лишнее или чего-то не хватает?
3. Один телефон или email без имени мы алертом не считаем — так же рассудил Верховный суд в одном деле, — но скор от него сильно растёт. Телефон вместе с email, ФИО или адресом — уже алерт. Вам так подходит, или нужно срабатывать на любой номер?
4. Публичных людей тоже считаем: по закону то, что человек сам выложил в открытый доступ, остаётся ПДн. Значит, будут срабатывания на запросах вроде «расскажи про министра N». Это нормально, или таких лучше исключать?

## Интеграция и скоуп

## Приложение: черновик контракта сервиса

В раунд 2 не отправляется (вопрос о контракте отложен, см. «Отложено» в open-questions.md). Рабочий черновик для задачи #12 (`Kopylov-Andrey`).

**Запрос** — на каждое новое сообщение:

```json
{
  "session_id": "s-123",
  "message_id": 7,
  "role": "user",
  "text": "Мой номер 8-900-000-00-00, я Маша из бухгалтерии",
  "previous_assistant_message": "Как с вами связаться?"
}
```

- `role`: `user`, `assistant` или `tool` (вывод инструментов в harness).
- `previous_assistant_message` — опционально (вопрос 5).
- Список сообщений обрабатываем как пакет: по каждому вернём отдельный ответ в порядке `message_id`.

**Ответ** — формат NER плюс `session_verdict`:

```json
{
  "session_id": "s-123",
  "message_id": 7,
  "entities": [
    {"type": "PHONE", "start": 10, "end": 25, "score": 0.98, "zone": "orange", "person_id": "p1"},
    {"type": "FIRST_NAME", "start": 29, "end": 33, "score": 0.95, "zone": "yellow", "person_id": "p1"},
    {"type": "WORKPLACE", "start": 37, "end": 49, "score": 0.81, "zone": "yellow", "person_id": "p1"}
  ],
  "message_verdict": {"has_pii": true, "max_zone": "orange"},
  "session_verdict": {
    "is_pii": true,
    "level": "alert",
    "first_violation_message_id": 7,
    "persons": [
      {
        "person_id": "p1",
        "alert": true,
        "rule": "score",
        "score": 0.86,
        "markers": [{"message_id": 7, "type": "PHONE"}, {"message_id": 7, "type": "FIRST_NAME"}, {"message_id": 7, "type": "WORKPLACE"}],
        "special_category": false
      }
    ]
  }
}
```

- `level`: `none` — ПДн нет; `warning` — скор выше заданной доли порога, раннее предупреждение; `alert` — нарушение.
- `rule` — почему алерт: `red_marker` (красный маркер), `two_orange` (два оранжевых), `score` (скор выше порога).
- `persons` — уровень и скор по каждому человеку в сессии.

**Что хотим уточнить:**
- Совпадает ли `entities` с форматом вашего NER API (поля, названия типов, смещения в символах)?
- Где хранить состояние сессии: на нашей стороне по `session_id` (тогда нужен срок хранения), или HiveTrace передаёт состояние в каждом запросе?
- Нужны ли `persons` и `score`, или достаточно `is_pii` и номера сообщения нарушения?
