# Session PII — сессионная детекция ПДн

## V1.

### 1. Проблема

В многоходовых сессиях LLM отдельные сообщения могут не содержать явных ПДн, но при накоплении контекста сессия становится сессией с ПДн, нарушение ФЗ-152, штраф. Это является актуальной проблемой для компаний, которые подключают для своих сотрудников внешние API. Пример: «Меня зовут Маша» → «У мамы фамилия Смирнова» → «Отправь от моего имени заявку, телефон и адрес следующие:...». Изолированно сигналы безобидны; вместе — уже опасная утечка личный данных сотрудника и/или компании в сеть.

Большинство уже существующих проверок ПДн концентрируются на уровне одного сообщения (turn-level), либо на полном готовом диалоге, они не отслеживают накопление ПДн динамически на уровне сессии (cross-turn) и систематически пропускают случаи утечки ПДн - пока диалог закончится, сотрудник может передать немалое количество конфиденциальной информации модели. Кроме того, большинство подходов страдают от деградации качества извлечения пропорционально увеличению объема контекста (падает recall), и не справляются с ситуациями, когда в рамках одного диалога может меняться язык/обычный текст может перемежаться с кодом или документацией [S14, S15, S16].

### 2. Задача
Таким образом, нам необходимо создать систему, которая не будет перегружена по памяти, хорошо справляется с извлечением ПДн для нескольких сущностей одновременно, а также способна работать не статически, а динамически - т.е. вычислять риск после каждого хода. Работа CAMP [S17] формализует ситуацию накопления утечек ПДн и формирования при их суммировании идентифицируемого личного профиля как Cumulative PII Exposure (CPE) - предлагаемый нами перевод для использования в дальнейшем - Совокупная утечка ПДн (СУП).

Формализуя, нам необходимо разработать сессионный модуль для вычисления СУП, который при каждом новом сообщении:
1. Извлекает сигналы с потенциальными ПДн (сущности, атрибуты, паттерны).
2. Атрибутирует их к своему источнику, которых может быть несколько (пользователь / коллега / родственник / иное третье лицо).
3. Накапливает score риска с привязкой к своему источнику (entity isolation).
* Мы можем добавить в проект граф с сущностями, где для каждой связанной сущности присваивается свой вес и score вычисляется на основе накопленного графа, поскольку они также могут влият на градус утечки друг друга (ФИО сотрудника + адрес + данные о проекте/ЛК = утечка данных о компании) [S17]. Обновление инкрементальное.
4. Определяет момент перехода — номер сообщения, после которого сессия впервые становится ПДн-сессией.
5. Модуль должен работать с бюджетом латентности, не растущим линейно с длиной сессии.
6. Измеряется собственная задержка сервиса в миллисекундах; TTFT внешней LLM или агента не входит в наш бюджет. Численный бюджет выбирается после baseline.

### 3. Границы MVP
Входит в MVP:

Сценарий: текстовый диалог "пользователь + чат-бот".
Язык: русский (допускается английский для тестовых датасетов).
Тип сигналов: именованные сущности (PER, LOC, ORG), контактные данные (телефон, email), явные идентификаторы (номер документа), связки «имя + фамилия + принадлежность».
Механизм линковки: rule-based + лёгкая модель NER; без тяжёлых LLM-вызовов на каждом сообщении.

Не входит в MVP:
* Сессии с агентами, извлечение ПДн из кода, логов, JSON, tool calls.
* Мультимодальные данные (изображения, аудио).
* Автоматическое исправление/маскировка (только детекция и флаг).
* Адаптивные атаки (adversarial evasion).

### 4. Определение момента перехода
Эталонный момент `t_gold` — первое сообщение, на котором по согласованной
политике требуется алерт. Учитываются только текущее сообщение и предыдущий
контекст, без пересмотра прошлого по будущим сообщениям. Позднейшее исправление
фактов не отменяет исторический первый момент. Пока размечаются первый момент
и флаг дополнительных положительных моментов.

Конкретные достаточные сочетания атрибутов, веса и пороги требуют согласования
с задачей данных; перечисление сочетаний само по себе не доказывает
однозначную идентифицируемость человека. Атрибуты группируются по локальным
ID людей; один явно общий атрибут может принадлежать нескольким людям.
«Неопределённо» — служебная группа неизвестной принадлежности, а не один человек.

Неуверенность в эталонном наличии утечки или первом моменте отмечается как
`unknown`, учитывается отдельно и исключается из основных сессионных метрик.
См. [метрики](../kb/metrics.md) и [проект ТЗ](../data/metrics-annotation-requirements.md).

### 5. Критерии успеха
1. Есть бэнчмарк - размеченный набор диалогов с указанием номера триггерного сообщения для каждой ПДн-сессии.
2. Есть собранный работающий модуль, который:
* динамически анализирует сессию с пользователем, извлекает сущности и корректно связывает их (entity isolation), накапливая score.
* Основная итоговая оценка — F2-timely: первый алерт точно на первом эталонном моменте.
* F2-session проверяет обнаружение независимо от позиции; offset на TP-session
  показывает ранние и поздние алерты; FP0 — ложные тревоги на отрицательных сессиях.
3. Время обработки измеряется по [методике](../kb/latency-budget.md): прогретый
сервис, конкурентная нагрузка, одна машина. Цели и допустимый рост после baseline
согласуются отдельно; пока численного критерия приёмки нет.

Сравнение с проверкой одного сообщения (#27): одинаковые данные, извлечение
и эталонная политика; в варианте без накопления состояние сбрасывается перед
каждым сообщением. Сессионный алерт этого варианта определяется наличием любого
алерта по сообщениям. Публикуются обе F2, FP0 и доля положительных сессий,
которые пропустил вариант без накопления. Доля считается как
`FN_session_without_state / N_positive`; отдельно показывается, какие из них
обнаружены сессионным вариантом. Это план эксперимента, не полученный результат.
