## Что уже решено и повторно спрашивать не нужно

Основание: merged PR #14 и раздел «Решено» в `open-questions.md` основной ветки.

| Вопрос | Зафиксированный ответ | Что ещё не следует из ответа |
|---|---|---|
| Формат модуля | Сервис, идентификация сессии через session_id; результат сообщения и сессии | Конкретная JSON-схема, жизненный цикл и интеграция ещё не утверждены |
| Способ анализа | Новое сообщение и накопленное состояние; без повторного NER истории | Постоянная стоимость линковки и памяти не доказана |
| Чьи данные | Пользователь и третьи лица | Способ связывания упоминаний ещё не выбран |

| Приоритет ошибок | F2, полнота важнее точности | Единица оценки и штрафы за ошибку момента ещё не согласованы |
| Исходный детектор | Regex + GLiNER как baseline, выбор открыт | Причина рекомендации ментора и совместимость с внутренним production API неизвестны |
| Железо | Для разработки достаточно CPU; приведён ориентир существующего production-детектора | Это не утверждённый бюджет нашего сервиса |
| Применение | Чат-боты и agent harness в общей постановке | Включение harness в MVP ещё открыто |
| Ближайший чекпоинт | Обзор источников и направлений проекта | Работающий полный сервис на этот этап не требуется |

синтетические данные. Организация работы зафиксирована в merged PR #1/#9/#15.

## Несогласованности, которые мешают считать ответы окончательными

- **Разные основания алерта.** В #19 постановка приводит имя + фамилию
  как пример достаточного набора. В #16 полное ФИО без других сведений
  не вызывает алерт. До устранения разметчики могут выбрать разные моменты.
- **Прямой идентификатор внутри #16.** В определении к нему отнесено полное ФИО,
  далее ФИО находится в оранжевой зоне и само по себе недостаточно. Следует
  согласовать терминологию определения и предлагаемой политики.
- **Неопределённая атрибуция.** Возможное агрессивное объединение из
  open-questions.md и консервативный unknown в #20 — разные политики, а не
  уже достигнутая договорённость.
- **Роли и покрытие.** В #20 раздел «Роли» условно связывает неполное покрытие
  с ожиданием анализа assistant/tool, но validate_pair требует его для любого
  not_in_scope. При передаче assistant обычный диалог без исторического алерта
  становится unknown до reset. Нужно согласовать, покрытие какой области оцениваем.
- **MVP и язык.** В #19 harness исключён и допускается английский для тестовых
  датасетов; основной сценарий ментора шире, рабочий язык — русский. Это
  предложения границ, а не подтверждённые изменения требований.
- **Граф и корпоративные сведения.** В #19 пример расширяет задачу на утечку
  сведений о компании. Это не тождественно накоплению ПДн физлица из #16;
  нужен отдельный scope, если направление сохраняем.
- **Оценка момента.** В #19 TP требует допустимого расстояния, но исходные
  определения не распределяют все ранние и поздние алерты по исходам.
  Комментарий F2-timely предлагает исправление, но в файле его ещё нет.
- **Эталон скора.** CPE Match Rate в #19 требует числовой эталон, хотя формула
  и шкала ещё не выбраны. Проверка вычисления заданной формулы и проверка
  качества самой формулы должны быть разделены.
- **Постоянное время.** #19 выводит независимость времени от истории из
  инкрементального хранения. #20 корректно отмечает зависимость линковки и
  памяти от числа людей/фактов. Нужны ограничения структуры и измерения.
- **Задержка.** #19 предлагает общий TTFT-бюджет; ревью лида просит бюджет
  своего сервиса. Production-ориентир ментора, литературные измерения и
  локальный CPU-прогон #20 нельзя объявлять одним бюджетом или сравнивать напрямую.
- **Источники и новизна.** PII-TRACE уже присутствует в #19 как S18; повторно
  добавлять его как неизвестный проекту источник не нужно. Заголовок этой
  записи не совпадает с названием статьи, как уже отмечено в локальном ревью.
  Нужны корректная библиография и различение покрытия упоминаний, линковки
  признаков человека и оценки момента. CAMP в #19 — описание пакета, не
  доказательство эффективности всех предлагаемых механизмов.

## Готовность к merge: дополнительная проверка

Повторно проверены состояния GitHub и CI; head-коммиты #16/#19/#20 не изменились.
Команда проверки из корня репозитория:

```powershell
foreach ($prNumber in @(16,19,20)) {
    gh pr view $prNumber --json headRefOid,mergeable,mergeStateStatus,reviewDecision,statusCheckRollup,reviews,comments
}
```

- #16: CLEAN, APPROVED, pre-commit успешен. Можно сливать как исследовательский
  черновик, сохранив явный статус предложений; не считать это подтверждением
  классов/правил ментором и не закрывать #10 как завершённую задачу. Желательно
  до merge согласовать формулировку про ФИО и обновить статус отправки классов.
- #20: MERGEABLE, но REVIEW_REQUIRED/BLOCKED; pre-commit успешен. Материалы
  исследования можно принимать без реализации всех новых задач. Перед merge
  исправить расхождение ролей/coverage, сохранить draft/proposed для нерешённого
  и получить требуемый approve. Исторический вердикт может оставаться явно
  обозначенным предложением до решения команды.
- #19: MERGEABLE, но REVIEW_REQUIRED/BLOCKED; pre-commit успешен. Пока не
  рекомендуется merge: неполный протокол метрик, конфликт оснований алерта,
  неучтённые замечания к задержке и необоснованный эталон скора затрагивают
  содержание будущего источника истины. Сначала исправления и повторное ревью.

Успешный pre-commit не является повторным запуском CPU-эксперимента и не
подтверждает корректность всех формул. Порядок #16 → #20 → исправленный #19
позволяет сверять последующие материалы с основной веткой. После каждого
merge нужно перепроверять конфликты реестра источников и CI следующих PR.
