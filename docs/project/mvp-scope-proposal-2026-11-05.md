# Направление проекта и узкий MVP

Дата: 2026-11-05. Статус: предложение для команды на основе текущих PR,
ответов ментора и позиций лида в обсуждении. Это описание, не реализация,
не принятый ADR и не автоматически согласованная инструкция по разметке.
Позиции остальных участников в предоставленной таблице ещё не заполнены.

## Куда движемся

Проверяем, помогает ли накопление фактов по конкретному человеку находить
сессионные случаи, которые пропускает проверка отдельных сообщений, и
насколько точно определяется первое сообщение срабатывания. Для этого
строим небольшой локальный сервис для русского текстового чата.

Детектор извлекает признаки из нового сообщения; сессионный слой связывает
их с людьми, исключает повторный учёт, обновляет состояние и выдаёт вердикт.
Новизну самого принципа накопления не заявляем: близкий научный аналог найден.
Ожидаемый результат проекта — проверенная русская постановка, воспроизводимый
набор с моментом срабатывания и измеренный вклад сессионного слоя.

## Обязательное ядро

| Область | Предлагаемая первая версия |
|---|---|
| Вход | Законченное сообщение user, session_id, последовательный message_id; русский обычный текст |
| Роли | Извлекаем факты только из user. Assistant не является обязательным контекстом, tool не входит в область первой версии |
| Извлечение | Закреплённый regex + GLiNER из исследования; адаптер к общим типам и исходным границам фрагментов |
| Люди | Пользователь и явно обозначенные третьи лица; простые правила привязки, без универсального разрешения кореференции |
| Факты | Нормализованное значение, тип, связь с человеком, ссылка на сообщение/фрагмент; повтор не повышает скор |
| Общие факты | Один явно общий факт может относиться к нескольким людям; в состоянии каждого учитывается однократно |
| Риск | Непосредственные правила для сильных оснований плюс счётчик разных слабых признаков одного человека с порогом |
| Выход | Извлечённые признаки, результаты по людям и сессии, первое сообщение алерта и основания |
| Состояние | Память процесса для исследовательского сервиса; явный reset, обнаруживаемая потеря состояния, изоляция сессий |
| Надёжность | Проверка порядка сообщений и отсутствие повторного накопления при точном retry; полноценный промышленный lifecycle не обязателен |
| Данные | Только синтетика, исходные сессии вне git, версия разметки и независимая проверочная выборка |
| Оценка | Своевременность как основной ориентир; наличие алерта и ошибки извлечения/линковки — диагностика |

Если сервис допускает передачу assistant как контекста транспорта, пропуск
его содержимого не означает неполное покрытие заявленной области user.
Валидатор и API должны отражать эту выбранную область. Неподдерживаемую роль
можно явно отклонить; она не превращает обычный поддерживаемый чат в unknown.
Поддержка слотов вида «серия паспорта?» → отдельные цифры в первой версии не обещается.

Batch, если сохраняется в API, является последовательной обработкой тех же
сообщений с теми же промежуточными результатами. Если мешает сроку, внешний
batch-endpoint откладывается, а проигрывание датасета выполняет клиент.

## Признаки: минимальное покрытие и очередь расширения

Первое обязательное покрытие: телефоны, email, точные адреса, паспорта,
СНИЛС, ИНН физлиц, карты; ФИО и его части; город, возраст/дата рождения,
организация/место работы и явно названная должность. Простые слова отношений
нужны для выделения третьего лица и явно общих фактов, а не для общего графа.

Общий PERSON ещё не различает полное ФИО и части: это отдельная задача адаптера.
Составление полного ФИО из частей допускается только после их привязки к одному
человеку. Повтор полного ФИО и его частей не считается новой независимой информацией.

Пол и отдельный флаг особых категорий остаются в согласованном направлении,
но расширенное семантическое покрытие предлагается добавлять после проверки
ядра. Это предлагаемая очередность реализации, не заявление о готовности
всего списка классов. Если команда требует их в обязательном MVP, это следует
явно зафиксировать до основной разметки и обеспечить примерами.

## Рабочая политика алерта и открытые края

- Документные прямые идентификаторы: отдельное непосредственное срабатывание.
- Телефон: для baseline предлагаем непосредственное срабатывание на распознанный
  личный телефон, учитывая направление нового ответа ментора на полноту.
  Это не правило «любая последовательность цифр — алерт». Корпоративные контакты
  и спорные случаи нужно явно описать в таблице, а не решить молча.
- Полное ФИО, email и точный адрес: предлагаем сохранить сильными маркерами;
  сочетания сильных маркеров одного человека дают непосредственный алерт.
  Полное ФИО само по себе не объявляем достаточным. Это предложение лида,
  а не доказанный универсальный критерий закона.
- Части ФИО и прочие слабые признаки: простой счётчик разных нормализованных
  атрибутов одного человека. Порог выбираем на development и фиксируем до test.
- Ни счётчик, ни score модели извлечения не называем вероятностью идентификации.
- Одиночный email и достаточность конкретных сочетаний — решения для небольшой
  таблицы разметки; не следует автоматически распространять ответ о телефоне
  на все контакты. Конкретную таблицу нужно принять до замораживания test.

Отдельно проверяем случаи без немедленного прямого идентификатора: иначе
алерты по телефону скроют качество накопления слабых признаков.

## Общий факт и вывод по родству

В синтетическом примере «мы с мамой живём по одному адресу» адрес явно относится
к обоим людям. Один факт связывается с обоими; отдельная графовая система не нужна.

Пример «меня зовут X, фамилия моей мамы Y» другой: имя относится к пользователю,
фамилия — к матери. Общая фамилия прямо не заявлена. Автоматически получить
фамилию пользователя нельзя. Даже при поддержке общей принадлежности факта
это остаются разные люди, а не один слитый профиль.

Универсальные выводы по родству, фамилии/отчеству и цепочкам людей откладываем.
Сложную неоднозначность показываем явно, без скрытого присвоения факта.

## Что исключаем из обязательного MVP

- Агентные сценарии, tool calls, структурированный код/JSON и разбор логов;
  небольшая проверка переноса возможна после готовности чатового ядра.
- Анализ фактов assistant и зависимое от него восстановление фрагментов анкеты.
- Исправления, отрицания, отзыв и перенос ранее накопленного факта между людьми.
- Специальную обработку публичных лиц, вымышленных персонажей и заявлений
  «данные ненастоящие». Такие случаи не должны попадать в основной тест с
  неоднозначным эталоном; их можно выделить отдельно как неподдерживаемый срез.
- Общий граф отношений и автоматические выводы о новых людях или атрибутах.
- Обученную шкалу риска, популяционную модель информативности и сложные веса.
- Полную реализацию Commit Gate: сначала накопление без него, затем абляция при
  наличии ресурса и понятной ошибки, которую он должен исправить.
- Маскирование, блокировку реального провайдера, UI, внешнюю LLM на каждом сообщении.
- Промышленную persistence, распределённую конкурентность, сложное управление
  TTL/эпохами; необходимые ограничения и явную потерю состояния всё равно описываем.
- Обязательное сравнение всех кандидатов в детекторы и перенос leaderboard как
  доказательства качества нашей системы.

Исключение среза из MVP не означает признать содержащиеся в нём сведения
безопасными. Система выдаёт результат в заранее заявленной области применения.

## Как определяем успех

Основное предложение — F2-timely для первого алерта без допуска на опоздание.
F2-session отвечает на дополнительный вопрос, распознаётся ли положительная
сессия вообще. Offset считаем среди сессий, в которых алерт был, и сохраняем
знак; пропуски показываем отдельно.

Нужно перед реализацией метрик утвердить полную таблицу исходов. Предложение
из комментария к #19: точный алерт даёт TP, поздний/отсутствующий — FN,
ранний в положительной сессии — FP и FN, алерт в отрицательной — FP.
Так ранняя остановка штрафуется и за необоснованный алерт, и за непопадание
в эталонное событие. Позиция лида явно поддерживает ранний FP и поздний FN,
но двойной учёт раннего события ещё требует подтверждения команды.

Unknown не удаляем из оценки. В положительной сессии без своевременного алерта
это пропуск; отдельно показываем долю отказов и область поддерживаемых случаев.
Не смешиваем неопределённость принадлежности с заранее исключённой ролью.

Эталон момента задаётся принятой инструкцией и проверкой разметчиков, а не
пересчитывается под каждый сравниваемый детектор или порог. Если правила
момента получаются непосредственно из фиксированного счётчика, честно
отделяем проверку реализации этой политики от доказательства реальной
определяемости человека. Численный «эталон риска» для MVP не обязателен.

Задержку измеряем в границах своего сервиса, отдельно извлечение и обновление
состояния. Указываем hardware, длину сообщения, число людей и фактов, версии.
Проверяем рост памяти и времени, не выводим постоянную стоимость из самого
слова «инкрементальность». Численный бюджет и целевую F2 определяем после baseline.

| Подключение извлечения | Адаптер regex + GLiNER, части ФИО, нормализация и конфликты; разбор ошибок | #12/#21/#24, PR #20 |
| Проверка гипотезы | Отдельное сообщение → накопление без людей → накопление по людям; одинаковые входы, данные и политика | #27 |
| Сервис и ресурсы | API нового сообщения, reset/retry, измерения задержки и памяти, воспроизводимый запуск | #28/#29 |

Не ждать полного исследования всех вариантов до первого baseline. Задача #23
даёт потенциальное улучшение после него. Метрики и корпус всё же нужно
зафиксировать до финального сравнения; это не факультативная надстройка.

Пилотные сценарии: один человек с фактами в разных сообщениях; пользователь
и родственник с разными признаками; явно общий адрес; повтор одного факта;
полное ФИО и его части; обычные числа и упоминания, не дающие достаточного
раскрытия; сильный идентификатор; длинный промежуток между связанными фактами.
Все примеры синтетические, исходные данные вне git.

## Что должно быть показано на MVP

Работающий API, демонстрация обновляемого состояния по людям и момента
алерта, версия синтетического набора и инструкции, воспроизводимый отчёт
сравнения с проверкой отдельных сообщений, измерение собственных ресурсов
и список известных ограничений. Дата MVP по roadmap — 01.12.2026, но этапы
выше не являются оценкой длительности или обязательствами участников.

До старта нужно согласовать только блокирующие края: телефон/email и
сочетания, полный подсчёт F2-timely, правила неуверенной атрибуции и явной
общей принадлежности факта. Всё остальное ограничивается описанным ядром
и расширяется после первого измеряемого результата.
