# Возможные задачи по линкеру

Дата: 2026-11-08. Статус: черновик для обсуждения, не утверждённый план
и не архитектурное решение. Исполнители и сроки не назначены; задачи
на GitHub по этому черновику не создавались.

Цель: получить первую проверяемую реализацию принадлежности атрибутов людям
в сессии, независимо от конкретного NER. Расчёт скора и решение об алерте —
отдельный потребитель состояния линкера.

Контракт NER и API рассматривается в [PR #20](https://github.com/TanellD/session-pii-detector/pull/20),
протокол оценки — в [PR #19](https://github.com/TanellD/session-pii-detector/pull/19).

## A. Состояние сессии и общий формат входа

**Что сделать:**

- Согласовать с NER, разметкой и оценщиком формат сообщения и извлечённого
  атрибута: тип, значение, границы, источник и устойчивый ID упоминания.
- Описать человека с локальным ID, упоминание, нормализованный факт,
  принадлежность и происхождение сведений. Уточнить различие этих объектов.
- Поддержать несколько владельцев явно общего атрибута и неизвестную
  принадлежность без утверждения единого владельца.
- Реализовать реестр в памяти: создать человека, добавить сведения,
  прочитать состояние, сбросить конкретную сессию.
- Зафиксировать порядок обработки внутри сессии и базовое поведение
  повторного запроса. Сессии не должны смешиваться.

**Результат:** описание структур и работающий реестр. Для первой проверки
владелец задаётся явно, автоматическая линковка ещё не нужна.

**Готовность:** можно последовательно загрузить синтетические сведения,
получить состояние по людям и сбросить одну сессию без изменения другой.

**Вне задачи:** промышленная БД, распределённая обработка, окончательный TTL,
формула риска. Ограничения хранения описываются совместно с #29.

## B. Нормализация и устранение повторов

Связано с #24. Зависит от формата A; примеры можно готовить параллельно с A.

**Что сделать:**

- Приводить к согласованному представлению значения поддерживаемых классов.
- Разрешать совпадения и конфликты regex/NER на одном фрагменте.
- Связывать повторные упоминания с одним фактом, сохраняя их происхождение.
- Описать перекрытие полного ФИО и частей, не добавляя искусственно новую информацию.
- Не выводить общего владельца только из совпадения значения: один атрибут
  может принадлежать нескольким людям.
- Разделить нормализацию без знания владельца и окончательное разрешение
  повторов после линковки. Согласовать этот порядок с C.

**Результат:** функции нормализации и таблица решений по дублям и конфликтам.

**Готовность:** повторы не создают лишние факты, исходные упоминания сохраняются,
разные владельцы не объединяются автоматически. Проверено на синтетических случаях.

## C. Baseline определения владельца

Связано с #21. Зависит от формата A, согласуется с B и D.

**Что сделать:**

- По новому сообщению, его атрибутам и предыдущему состоянию выбрать:
  существующий человек, новый человек, несколько явно общих владельцев
  или неизвестная принадлежность.
- Начать с явных указаний о себе, третьих лицах и простых ссылок на людей.
- Сохранять основание назначения для разбора ошибок.
- Не использовать будущие сообщения и не выводить автоматически общие
  фамилию, адрес или другие атрибуты только по родству.

**Результат:** простой запускаемый линкер и описание поддерживаемых конструкций.

**Готовность:** на эталонных атрибутах различает людей, связывает сведения
между сообщениями и воздерживается при недостаточных основаниях.
Предлагаемый минимальный набор сценариев: один человек, разные люди,
новый человек, явно общий факт и неоднозначность.

**Вне задачи:** универсальные выводы по графу отношений, обучение сложной модели,
внешняя LLM на каждом сообщении. Поддержка исправлений требует отдельного решения.

## D. Неуверенная принадлежность

### Пометка от 12.11.2026: идея «мусорного лица»

Есть идея завести «мусорное лицо» — служебную группу «неопределённо», куда
попадают все извлечённые атрибуты, которым линковщик не нашёл владельца.
Это идея для проверки при выборе архитектуры, а не принятое решение.
Попадание в эту группу само по себе не подтверждает общего владельца атрибутов.
Правила последующего назначения владельца и использования группы в политике
алерта требуется обсудить отдельно.

Связано с #22. Минимальные правила нужны до сборки C; углублённое исследование
не должно задерживать baseline.

**Что сделать:**

- Описать условия воздержания от назначения владельца.
- Хранить неизвестные сведения в служебном «неопределённо», не трактуя их
  как данные одного человека и не смешивая с неуверенным эталоном разметки.
- Решить, допустимо ли уточнять принадлежность позднее и какое происхождение
  изменения сохранять. Не включать сложные исправления в MVP автоматически.
- Определить машинное представление неизвестной принадлежности для оценщика.

**Результат:** минимальные правила и представление неизвестной принадлежности.

**Готовность:** неоднозначность видна в результате; нет скрытого присвоения
атрибутов человеку. Примеры одинаково понимаются разработчиком и разметчиком.

**Вне задачи:** выбор повышенного порога алерта для неизвестной группы.
Это отдельная гипотеза политики риска, не поведение линкера по умолчанию.

## E. Интеграция и оценка линкера

Зависит от A–D, общего формата NER и первой версии оценщика.
До готовности оценщика возможна функциональная проверка, но не итоговый отчёт качества.

**Что сделать:**

- Собрать обработку: выход NER → нормализация → определение владельца →
  разрешение повторов с учётом владельца → обновление состояния.
- Сначала прогнать эталонные атрибуты, затем реальный выход выбранного NER
  на тех же сессиях. Эти результаты не смешивать.
- Проверить принадлежность по шагам; способ агрегации согласовать с оценщиком.
- Разбирать ошибки объединения людей, разделения одного человека,
  общей принадлежности, неизвестных владельцев и повторов.
- Подключить согласованные метрики из PR #19; B-cubed использовать только
  в явно определённой области применимости.

**Результат:** воспроизводимый прогон, отчёт по шаблону эксперимента,
ограничения и перечень следующих исправлений.

**Готовность:** указаны версии синтетических данных, конфиги, коммиты и команды;
видно, какие ошибки относятся к NER, а какие — к линкеру.
Численные цели выбираются отдельно после baseline.

## Отдельно: накопление и алерт

После появления состояния A можно разрабатывать отдельный модуль политики:
получить факты по людям, вычислить скор, вернуть текущий результат
и исторический первый алерт. Формула, порог и правило для «неопределённо»
должны быть согласованы отдельно. Эта работа не скрывается внутри задачи C.

## Предлагаемый порядок

Сначала согласовать формат A и минимальные правила D. После этого B и C
можно разрабатывать параллельно с регулярной совместной проверкой.
Затем E объединяет их с NER и оценщиком. Подготовка ТЗ разметки идёт параллельно,
но единицы атрибутов и владельцев должны быть согласованы до фиксации данных.

Во всех примерах и проверках — только синтетика. Исходные данные вне git;
эксперименты оформляются по правилам репозитория. Этот черновик не назначает
исполнителей, не меняет существующие issues и не добавляется в PR Олеси.
