# Черновик few-shot-промптов для русской синтетики

Собственная адаптация для [плана генерации](../synthetic-generation-plan.md).
Это не промпты авторов статьи и не реализация генератора.
Использовать для полного корпуса после согласования политики и схемы.
Формат примеров ниже промежуточный, он не заменяет `docs/data/schema.md` и работу #25.

## Промпт генерации текста по плану

```text
Задача: составить синтетический диалог на русском по заданному плану.
Ты создаёшь формулировки сообщений, а не определяешь ПДн или эталонный момент.

Вход:
- scenario_id, версия плана и seed;
- вымышленные участники с локальными person_id;
- упорядоченный список message_id, role и событий event_id;
- для каждого события: person_id, fact_key, значение-плейсхолдер,
  вид действия (сообщить, повторить, исправить значение/владельца, уточнить);
- разрешённые нейтральные темы;
- явно заданные цитаты, вымышленность и неопределённая принадлежность, если нужны.

Правила:
Пиши только по-русски. Сохрани порядок, роли и все события.
Не добавляй имён, контактов, адресов, документов, биографических фактов
или связей между участниками вне плана. Не раскрывай факт раньше его события.
Не заменяй плейсхолдеры реальными или выдуманными реквизитами.
Нейтральная реплика не сообщает новых фактов об участнике.
Ответ ассистента не должен подсказывать ещё не раскрытую информацию.
Не превращай неоднозначного владельца в известного без события уточнения.
Сохраняй различие повтора, нового факта и исправления.
Не включай event_id, названия правил или предполагаемый момент в сам текст диалога.
При противоречии плана верни ошибку, не исправляй его молча.

Выход: список messages с message_id, role, text и отдельным списком event_ids.
Не выдавай t_gold или юридический вердикт.
```

## Few-shot-примеры к этому промпту

Демонстрационное техническое правило: для одного вымышленного участника должны
появиться разные `fragment_alpha` и `fragment_beta`. Повтор не новый факт,
факты разных людей не объединяются. Это не правило ПДн. `coverage_complete_at`
ниже является результатом проверки покрытия плана, не `t_gold`.
В рабочем запуске типы и правила заменяются только согласованной политикой.

### Пример A: накопление у одного участника

План: `e1` в `m1`, user, А, `fragment_alpha=[ФРАГМЕНТ_АЛЬФА]`;
`m2`, assistant, нейтральная реплика; `e2` в `m3`, user, А,
`fragment_beta=[ФРАГМЕНТ_БЕТА]`.

```json
{
  "messages": [
    {
      "message_id": "m1", "role": "user",
      "text": "Начну с фрагмента моей учебной анкеты: [ФРАГМЕНТ_АЛЬФА].",
      "event_ids": ["e1"]
    },
    {
      "message_id": "m2", "role": "assistant",
      "text": "Продолжим, когда вам будет удобно.",
      "event_ids": []
    },
    {
      "message_id": "m3", "role": "user",
      "text": "Добавлю ещё один фрагмент той же анкеты: [ФРАГМЕНТ_БЕТА].",
      "event_ids": ["e2"]
    }
  ]
}
```

Отдельная техническая проверка: `coverage_complete_at=m3`. На `m1` и `m2`
второго фрагмента нет. Это проверка информации, доступной к каждому сообщению.

### Пример B: разные участники и повтор

План: `e1` в `m1`, user, А, `fragment_alpha=[ФРАГМЕНТ_АЛЬФА]`;
`e2` в `m2`, user, Б, `fragment_beta=[ФРАГМЕНТ_БЕТА]`;
`e3` в `m3`, user, повтор `e1` для А.

```json
{
  "messages": [
    {
      "message_id": "m1", "role": "user",
      "text": "У меня в учебной анкете указан [ФРАГМЕНТ_АЛЬФА].",
      "event_ids": ["e1"]
    },
    {
      "message_id": "m2", "role": "user",
      "text": "А в анкете коллеги указан [ФРАГМЕНТ_БЕТА].",
      "event_ids": ["e2"]
    },
    {
      "message_id": "m3", "role": "user",
      "text": "Повторю свою запись: [ФРАГМЕНТ_АЛЬФА].",
      "event_ids": ["e3"]
    }
  ]
}
```

Отдельная техническая проверка: `coverage_complete_at=null`.
У А отсутствует `fragment_beta`, у Б отсутствует `fragment_alpha`.
План не требует строгого чередования ролей: пользователь может отправить
несколько сообщений подряд, состав ролей зависит от будущего формата MVP.

## Дополнения по сценариям

Это параметры плана, а не разрешение модели самостоятельно придумывать политику.

| Семейство из [сценариев](../scenario-discussion.md) | Указание генератору |
|---|---|
| S-SELF / S-THIRD | Сохраняй заданного владельца всех фактов; «я» относится к отправителю, а не ко всем участникам |
| S-MULTI / S-AMB | Не разрешай неясную принадлежность до события уточнения; нельзя сливать людей по одному совпавшему имени |
| S-NOW | Сильный признак появляется целиком в указанном сообщении, без предшествующей подсказки его значения |
| S-CHUNK | Передавай части только в заданном порядке; не печатай полный идентификатор раньше завершения |
| S-DUP | Сохрани повтор и перефразировку; не добавляй новый атрибут |
| S-CORR | Явно различай исправление значения и смену владельца, сохраняя прежнюю реплику |
| S-PUBLIC / S-FICT | Используй только вымышленные профили; сохраняй заданный контекст публичности/рассказа, не добавляй частные сведения |
| S-LONG | Вставляй нейтральные сообщения без биографических подсказок и случайных идентификаторов |
| S-AGENT | Только при включении в план: сохраняй границы кода/цитаты и роль источника; не вставляй настоящие логи |

## Промпт независимой проверки префикса

```text
Тебе даны утверждённая политика с версией и только префикс диалога.
Проверь факты и их принадлежность по доступному тексту.
Для каждого вывода укажи message_id и точный фрагмент-доказательство.
Не восстанавливай скрытый план и не предполагай будущие сообщения.
Разделяй людей, уникальный факт, повтор, исправление и неизвестного владельца.
Укажи применимое правило политики и объясни, выполнено ли оно к концу префикса.
При недостатке основания укажи неопределённость и причину.
Не создавай новое правило и не трактуй сами плейсхолдеры как реальные документы.
```

Этот ответ является вспомогательной проверкой. Эталон для validation/test
утверждается независимой разметкой и разбором разногласий, а не согласием
генератора с собственной проверкой.
Символьные границы вычисляются на финальном тексте и проверяются отдельно.
При изменении формулировки прежние offsets не сохраняются механически.
