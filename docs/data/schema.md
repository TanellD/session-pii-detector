# Формат разметки MVP

Версия: `annotation-mvp-v2`. [Правила](annotation-guidelines.md), [таблица классов](annotation-class-fields.md), [синтетические примеры](annotation-synthetic-examples.md). Используйте этот формат для новых аннотаций LLM с выборочной проверкой людьми. Он не ограничивает архитектуру детектора.

## Сессия и сообщения

Сессия содержит ровно `schema_version`, `session_id`, `messages`, `entities`, `case_flags`. Порядок массива `messages` задаёт порядок диалога. У сообщения только `id` и неизменный `text`. ID сообщений уникальны в сессии. Роли user/assistant и иные метаданные не требуются в этой минимальной версии; нужный состав сообщений определяется при подготовке корпуса.

## Сущность

| Поле | Значение |
|---|---|
| `id` | Уникальный ID упоминания внутри сессии, назначаемый инструментом. |
| `message_id` | ID существующего сообщения. |
| `start`, `end` | Целые индексы Unicode code points, интервал `[start, end)`. Это не байты и не индексы UTF-16 JavaScript; при переносе из браузера требуется преобразование. |
| `type` | Один из типов таблицы классов: отдельные Ф/И/О, контакт, адрес, красный документ, пол, география, профессия, организация. Типов `fio`, ФИ/ИО/ФО, местоимения и `relationship` в v2 нет. |
| `person_id` | Непустой локальный ID человека или `null` для неизвестной принадлежности. |

Дополнительные поля сущности запрещены валидатором. Значение равно `message.text[start:end]`; `value`, `complete`, `usage`, `exact`, `uncertain`, исправление и коэффициенты вручную не вводятся. Исправление — новая сущность в новом контексте; предыдущий спан сохраняется. Спаны непустые и не пересекаются, без предлога перед сущностью и внешних пробелов. ФИО и ФИ/ИО/ФО — только вычисляемые сочетания отдельных Ф/И/О одного человека.

## Флаги всего кейса

`case_flags` содержит ровно:

- `is_example`: boolean — учебная, техническая или вымышленная ситуация **в тексте**, а не просто синтетическое происхождение датасета;
- `annotation_uncertain`: boolean — неизвестно, требуется ли алерт; неизвестная принадлежность спана сама по себе флаг не включает;
- `clarification_reason`: `null` для определённого вердикта; иначе `insufficient_statistics` либо `specification_gap`. Старое `person_attribution` читается для совместимости.

При недостатке статистики обработчик может дополнительно выставить неуверенность всего результата и причину `insufficient_statistics`, даже если LLM не заметила пробел. Оригинальные сущности не переписываются. Флаг примера не отключает расчёт алерта: кейс с примером и сработавшим правилом допустим.

`annotation_uncertain` относится к вердикту алерта. `person_id=null` не включает флаг автоматически. Для определённого отрицательного вердикта флаг равен `false`, причина — `null`. Обработчик пересчитывает вычислительную отметку недостатка статистики. Общий контакт службы остаётся без персоны и не участвует в личном сочетании. Прямые «мой телефон», «моя почта», «я живу» относятся к говорящему без разрешения местоименных цепочек.

Вычислительный адаптер сам создаёт технические поля калькулятора из утверждений минимального формата: выделенное значение считается полным, известная персона контакта означает личную принадлежность, известная персона организации — конкретного работодателя, известная персона адреса — проживание. Если это нельзя утверждать по контексту, разметчик выбирает `null`. Привязка к персоне не проверяет реальное существование человека во внешнем реестре.

Маски и инициалы запрещены как части имени; для документа, адреса и организации полнота дополнительно проверяется разметчиком по инструкции. Валидатор не доказывает существование адреса/документа, не проверяет личность владельца и не заменяет NER. Неоднозначный нормализатор не имеет права автоматически приписывать сущность известному человеку.

## Минимальный пример

```json
{
  "schema_version": "annotation-mvp-v2",
  "session_id": "synthetic-format-example",
  "case_flags": {"is_example": false, "annotation_uncertain": false, "clarification_reason": null},
  "messages": [{"id": "m1", "text": "Я Тестимир."}],
  "entities": [
    {"id": "e1", "message_id": "m1", "start": 2, "end": 10,
     "type": "first_name", "person_id": "p1"}
  ]
}
```

Это вымышленное имя. Примеры с проверенными машинным способом границами содержатся в `tests/fixtures/annotation-mvp-cases.json`; их исходник — `tools/build_annotation_mvp_examples.py`.

## Вычисляемый результат

Разметка сущностей сохраняется отдельно от результата расчёта. `tools/annotation_contract.py` возвращает первый момент `first_alert` с `message_id`, `message_index`, `reason` и `context_entity_ids` либо `null`. `context_entity_ids` — контекст персоны для воспроизведения, не обещание минимального достаточного набора доказательств. Причина — `red_rule`, `combination_rule` или `candidate_count_rule`. У сообщения дополнительно рассчитывается `assessment`: `triggered`, `not_triggered`, `insufficient_data`.

При нескольких основаниях приоритет основной причины: красное → сочетание → численный путь. Контактная пара телефона/email относится к `combination_rule`. Полная статистическая оценка может отсутствовать при качественном алерте. Флаг отсутствия найденного момента не является доказательством отсутствия риска при неполной статистике.

LLM и проверяющий человек не размечают сущность повторно для задания причины. Проверка проводится по спанам, принадлежности, флагам кейса, первому сообщению и причине. Местоименная/родственная линковка и перепривязка прежних неизвестных сущностей не выполняются. Точные определения итоговых метрик качества остаются отдельной задачей `docs/kb/metrics.md`.

```powershell
python -X utf8 tools/annotation_contract.py --check-cases tests/fixtures/annotation-mvp-cases.json
# Локальный вход с тем же минимальным форматом; исходные значения в stdout не печатаются:
python -X utf8 tools/annotation_contract.py --input path/to/local-annotation.json
```
