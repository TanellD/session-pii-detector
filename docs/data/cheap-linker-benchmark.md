# Датасет и проверка дешёвых линкеров

Цель — заменить Gemma более дешёвым методом и сравнить качество владельцев,
алертов и время работы на одинаковых входах. Пакет использует существующий
синтетический `session-benchmark-2400-v5`; новой независимой разметки не создаёт.
Он подходит для обучения и сравнительного исследования, но не доказывает
качество на реальных чатах.

## Что внутри

`data/experiments/cheap-linker-benchmark-v1-2026-11-26`:

| Часть | Сессий | Назначение |
|---|---:|---|
| train | 1440 | Обучение модели или разработка правил |
| validation | 480 | Выбор линкера и порогов |
| test | 480 | Итоговая проверка зафиксированного метода |

В каждой части:

- `inputs/sessions.json`: только ID и пользовательские сообщения.
- `inputs/ner.jsonl`: сохранённый regex + GLiNER v2, до фильтрации сервисом;
  сообщения, спаны, типы, значения, provenance, полнота обработки.
- `targets/snapshot.json`: эталонные сущности, владельцы, первый алерт,
  группировка по людям/длине и пометки неопределённости. Только оценщику.
- `targets/linker-supervised.jsonl`: обучающие запросы и ответы с эталонными
  кандидатами и прошлым эталонным состоянием (teacher forcing).

Входы не содержат число людей, будущие сообщения, ожидаемые алерты или владельцев.
Полная сессия хранится для воспроизведения; линкер получает только текущий префикс.
Числа таблицы воспроизводятся командой сборки ниже; контрольные суммы — в manifest.json.
JSONL supervised содержит исходное полное окно предыдущих сообщений. Для обучения
под runtime с окном 3 следует обрезать request.previous_messages до последних трёх;
либо отдельно объявить другое окно и использовать его во всех сравниваемых методах.

Полные 480 validation входят в пакет, включая сессии, на которых Gemma ранее
завершалась ошибкой. Подмножество успешных Gemma не заменяет весь бенчмарк.
Нулевые/общие владельцы, служебные контакты и несколько людей сохраняются.
Неоднозначные части синтетических имён остаются ограничением исходного эталона;
их аудит описан в исследовательских заметках. Правила разметки здесь не меняются.

## Подключение своего метода

Создать, например, `tools/my_linker.py` с функцией `predict(request) -> dict`.
Не читать внутри неё targets, gold или разметку test. Модель загрузить один раз
при импорте модуля, а не заново для каждого сообщения. Метод должен быть без
скрытой памяти между сессиями: всё нужное состояние приходит в request.

Request содержит `message`, `previous_messages`, `candidates`, `known_people`,
`unowned_facts`. Кандидаты уже прошли штатные фильтры сервиса. Профили известных
людей построены из собственных прошлых ответов метода. В runtime нет эталонных
владельцев или подсказки о количестве людей.

Ответ должен назначить ровно один результат каждому candidate_id:

```json
{"assignments": [
  {"candidate_id": "c1", "owners": ["new:1"], "service_contact": false},
  {"candidate_id": "c2", "owners": ["new:1"], "service_contact": false}
]}
```

- ID из `known_people`: существующий человек.
- `new:1`, `new:2`: новые люди в текущем сообщении. Один new:N у нескольких
  кандидатов связывает их с одним новым человеком; в следующем запросе нужно
  использовать выданный runtime ID из known_people.
- `owners=[]`: неизвестный владелец; разные неизвестные не объединяются автоматически.
- Несколько owners: подтверждённая совместная принадлежность, не альтернативы.
- Служебный телефон/email: `service_contact=true`, `owners=[]`.
- Запрещено пропускать кандидаты, менять их границы или сливать людей по совпадению контакта.

JSON-контракт проверяется существующим парсером сервиса. Использование класса
GemmaLinker в оценщике означает повторное использование сериализации и валидации;
Gemma и внешний API при этом не вызываются. Функция predict может реализовать
правила, компактную модель или собственный API-клиент; стоимость последнего
нужно учитывать отдельно. Пакет не требует весов GLiNER для воспроизведения.

## Запуск и live-отчёт

Архив распаковать в отдельную папку. Команды выполнять из её корня либо из
исходного worktree. Python 3.11+, установка минимальных зависимостей:

```powershell
python -m pip install -r data/experiments/cheap-linker-benchmark-v1-2026-11-26/requirements.txt
```

Контрольные методы: `cheap_linker_baselines:all_unknown` и
`cheap_linker_baselines:one_person`. Первый оставляет всё неизвестным, второй
приписывает всё одному человеку; это диагностические ориентиры, не рабочие линкеры.

Первый терминал — полный сервис на замороженном реальном NER, без нового NER:

```powershell
python -X utf8 -u tools/run_linker_benchmark.py --package data/experiments/cheap-linker-benchmark-v1-2026-11-26 --split validation --mode real-ner --linker cheap_linker_baselines:one_person --run data/experiments/linker-one-person-validation
```

Второй терминал — автообновление документа каждые 15 секунд:

```powershell
python -X utf8 tools/watch_cached_validation.py --run data/experiments/linker-one-person-validation --interval 15
```

Открыть `run/online-progress.md`; числовая версия — `online-summary.json`.
Время обновления показывает активность наблюдателя, отдельно показана активность
worker. Для обновления один раз добавить `--once`. Наблюдатель не вызывает модель.
Для продолжения worker после остановки повторить его команду с `--resume`.
Не запускать два worker или два наблюдателя одного каталога. Новый метод,
модель, настройки, окно или политика требуют нового каталога запуска.
Для локальной модели включать хеши её весов и параметров в файл модуля-обёртки
или использовать новое имя run при любом изменении: runner хеширует файл модуля,
но не может обнаружить изменения произвольных внешних весов/API за ним.

Изолированная проверка линкера: та же команда с `--mode gold` и новым `--run`.
В ней кандидаты эталонные, а состояние всё равно строится по собственным ответам.
Это отличается от статических supervised-примеров с прошлым эталонным состоянием.
Для честного сравнения методов использовать одинаковые mode, окно и политику.

## Метрики после линкера

Runner пропускает выход через настоящий Pipeline и RiskEvaluator и сохраняет
все сообщения, даже после первого алерта. `predictions/session_id.json` содержит
владельцев, спаны и first_alert. `baseline-metrics.json` — итоговые метрики;
`failures/` — отдельные ошибки, которые не превращаются в TN.

Публиковать вместе:

1. F2-timely — основная метрика, F2-session и их precision/recall.
2. Число обработанных и ошибочных сессий; причины ошибок.
3. Pairwise P/R/F1 линкера только на точно совпавших спанах; число совпавших
   упоминаний и число всех эталонных. Высокий F1 на этом подмножестве не доказывает
   качество всей цепочки. Неизвестные эталонные владельцы исключены из pairwise;
   правильность отказа и служебности нужно проверять дополнительно.
4. Точность экстракции, FP0 на уверенно отрицательных и частоту ложных алертов
   среди всех отрицательных; группы 0–3 человека и длины — в отчёте калибровки.
5. Время вызовов линкера: медиана/p95 и доля кэшированных. Это последовательный
   замер, загрузка модели исключена; он не измеряет максимальный RPS.

Метрики следуют docs/kb/metrics.md. При точном первом алерте timely получает TP;
ранний — только FP; поздний/пропущенный — FN. F2 = 5TP/(5TP+4FN+FP).
Поэтому recall-timely не равен доле точных попаданий среди всех положительных.
Метрики успешных сессий при отказах условны. Для сравнения с Gemma считать
одинаковое пересечение session_id и отдельно показывать полное покрытие каждого
метода; исторический результат 448 сессий нельзя напрямую сравнивать со всеми 480.

## Подбор порогов по F2-timely

Сначала один проход линкера до конца сессий. Затем меняются только пороги риска;
повторять модель не нужно, потому что риск не входит в запрос линкера.

```powershell
python -X utf8 tools/calibrate_cached_risk.py --run data/experiments/linker-one-person-validation --thresholds-only
```

Порог известного владельца и порог неизвестной принадлежности перебираются на
сетке при фиксированных весах. Обязательные правила сохраняются. Основная цель
F2-timely; при равенстве — F2-session, затем минимальное изменение параметров.
Это максимум по проверенной сетке с ограничениями, не по всем возможным политикам.
При ошибках можно явно добавить `--allow-incomplete`; требуется минимум 90%
покрытия, результат помечается предварительным и содержит исключённые сессии.
Эта граница не устраняет смещение успешного подмножества.

Отчёт: `calibration/report.md`, JSON с параметрами, дельтами и группами,
`recommended-policy.json`. Live-документ подхватит результат автоматически.
Для повторного поиска нужен новый `--output` внутри data/. Без `--thresholds-only`
оценщик также ищет веса — это другой эксперимент, его нужно объявлять отдельно.
GLiNER confidence этот поиск не меняет.

Выбрать один метод и политику на validation, затем запустить test один раз:

```powershell
python -X utf8 tools/run_linker_benchmark.py --package data/experiments/cheap-linker-benchmark-v1-2026-11-26 --split test --mode real-ner --linker cheap_linker_baselines:one_person --policy data/experiments/linker-one-person-validation/calibration/recommended-policy.json --run data/experiments/linker-one-person-test
```

Подбор на test запрещён оценщиком. Пример one_person здесь заменить выбранным
методом. Старые подобранные под Gemma пороги не переносить как оптимальные для
другого линкера; сравнить фиксированную общую политику и отдельно политику,
подобранную для каждого метода только на validation.

## Сборка и происхождение

```powershell
python -X utf8 tools/prepare_linker_dataset.py --dataset data/experiments/session-benchmark-2400-v5-2026-11-26 --ner data/experiments/benchmark-ner-only-2026-11-26 --output data/experiments/cheap-linker-benchmark-v1-2026-11-26
```

Требуется новый output. Создаются каталог и ZIP с данными, кодом runtime и
конфигами, без весов моделей, секретов и кэша запросов. Manifest фиксирует
хеши данных и исходный NER. Спаны/владельцы происходят из авторских заготовок,
алерты — из калькулятора правил без весов сервиса. Ревью выборочное, независимого
человеческого подтверждения нет. Похожие программные варианты зависимы.
Оценки на этом наборе не заменяют отдельный реалистичный источник диалогов.
