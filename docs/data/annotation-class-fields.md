# Поля по классам: инструкция для LLM-разметчика

- Версия: `annotation-mvp-v2`.
- Все приведённые имена, адреса, компании и контакты вымышлены. Примеры документов — нулевые суррогаты формата, не существующие документы и не проверка контрольных сумм.
- [Общие правила](annotation-guidelines.md), [машинный формат](schema.md), [развёрнутые учебные разборы](annotation-synthetic-examples.md).

## Общие поля каждого выделенного упоминания

| Поле | Обязательность | Что заполняет разметчик / инструмент | Неизвестное значение |
|---|---|---|---|
| `id` | Обязательно | Уникальный ID упоминания, может назначить инструмент. | Не допускается. |
| `message_id` | Обязательно | Сообщение с исходным фрагментом. | Не допускается. |
| `start`, `end` | Обязательно | Границы `[start, end)` в Unicode code points, без внешних предлогов, пробелов и завершающей пунктуации. | Если границы не удаётся определить, кейс направляется на уточнение; фиктивные индексы не ставятся. |
| `type` | Обязательно | Один из классов таблицы ниже. | Не придумывать новый тип; спорный кейс пометить целиком. |
| `person_id` | Обязательно | ID существующей либо сразу созданной отдельной персоны. Персона может быть без имени. | `null`, когда связь с человеком не установлена; это не ID одной общей неизвестной персоны. |

Значение берётся из исходного текста по границам. Нормализация, зона, составные ФИ/ИО/ФО/ФИО, статистический вес и причина алерта вычисляются обработчиком. Их не размечают отдельными сущностями и не добавляют к сущности как ручные поля.

## Таблица классов

Для `phone`, `snils` и `age` принимается только цифровая запись значения. Разделители номера и единицы возраста допустимы. Словесные и смешанные числовые значения не выделяются этими типами и не нормализуются в цифры. Это ограничение MVP, а не самостоятельная причина новой пометки неуверенности; исторические пометки сохраняются.

Во всех строках обязательны общие поля выше. «Дополнительно» означает правила интерпретации и возможные будущие детали, **не обязательные дополнительные поля MVP**.

| Класс и зона | Что обязательно для этого типа | Дополнительно в MVP | Как поступить при неизвестности | Положительный пример: что выделить | Отрицательный пример: чего не выделять |
|---|---|---|---|---|---|
| Фамилия — `last_name`, жёлтая | Полная явно написанная фамилия; отдельный спан независимо от соседних имени/отчества. | Никаких ручных полей. Дефис и части составной фамилии сохраняются внутри значения. | Не угадывать структуру имени. Если нельзя выбрать Ф/И/О, весь кейс — на уточнение. При ясной фамилии, но неясном владельце, создать явно отдельную персону либо оставить `null`. | «Фамилия: **Тестов**». В «Тестов Тестимир Макетович» фамилия — только «Тестов». | «Фамилия начинается на Т.»; фамилия, предположенная из email или родства. |
| Имя — `first_name`, жёлтая | Полное явно написанное имя. | Никаких ручных полей; многословное полное имя допустимо. | Не достраивать инициалы. При неясной принадлежности — отдельная персона по явному контексту либо `null`. | «Имя: **Тестимир**»; «Тестов **Тестимир** Макетович». | «Т.»; часть имени внутри `testimir@example.invalid`. |
| Отчество — `patronymic`, жёлтая | Полное явно написанное отчество. | Никаких ручных полей. | Не образовывать отчество из имени отца. Отсутствие отчества не заполняется вымышленным значением. | «Отчество: **Макетович**»; «Тестов Тестимир **Макетович**». | «М.»; «отца зовут Макет» как источник автоматически достроенного отчества. |
| Телефон — `phone`, оранжевая | Полный телефон с кодом страны; разделители внутри номера сохраняются. | Признак полноты вручную не нужен: неполные значения не относятся к этому типу MVP. | Контакт приёмной/объекта не присоединять человеку. Если явно назван отдельный безымянный владелец, создать его персону сразу. | «Телефон: **+7 (000) 000-00-01**». | «Последние цифры — 0001»; маска `+7 (***) ***-**-**`. |
| Email — `email`, оранжевая | Полный адрес почты целиком. | Имя, организация и пол из адреса не достраиваются. | При неясном/организационном владельце `null`; не связывать лишь по близости к имени. | «Почта: **testimir@example.invalid**». | `testimir@…`; отдельное имя `testimir` внутри уже выделенного email. |
| Адрес — `address`, оранжевая | Полное значение до установленного дома с достаточным географическим контекстом; квартира необязательна. | В текущем MVP нет обязательных полей уровня адреса, типа дома или числа квартир. Уровень «дом/квартира» и тип жилья могут определяться обработчиком; без подтверждения не назначать численную оценку квартиры. | Адрес объекта не делать адресом проживания человека. Невозможность геокодирования не отменяет ясно выделяемую сущность; численный путь может остаться неуверенным. | «Проживает в **г. Макетоград, ул. Вымышленная, д. 1, кв. 2**» — предлог «в» снаружи. | Один город или улица без дома как `address`; вложенные повторные спаны города/улицы внутри того же полного адреса. |
| География — `geography`, жёлтая | Полное явно названное географическое место, например город/село/деревня/регион, когда это отдельное упоминание. | Тип населённого пункта и численность — задача справочника/обработчика. Не добавлять ручной коэффициент. | Одноимённое место не разрешать догадкой. Если точное место/население не определено, сущность сохраняется, численная разметка кейса требует уточнения. | «Проживание: **г. Макетоград**»; «из **села Макетного**» без предлога «из». | Регион, предположенный по телефонному коду; город как вложенный дубль уже размеченного полного адреса. |
| Пол — `sex`, жёлтая | Отдельно явно выраженное значение пола. | Никаких ручных полей. Не извлекать пол из имени, окончания отчества либо рода глагола. | Не угадывать; если явного значения нет, сущности нет. | «Пол: **мужской**», «Пол: **женский**». | «Макетович» или «я пришла» как самостоятельное доказательство отдельной сущности пола. |
| Профессия / должность — `occupation`, жёлтая | Явное название занятия/должности. | Код ОКЗ и варианты соответствия предлагает обработчик; они не обязательные ручные поля сущности. | «Менеджер» можно выделить, хотя точная группа неизвестна. Если это мешает вердикту, пометить весь кейс как неуверенный. | «Должность: **инженер-проектировщик**». | Название организации как профессия; профессия, предположенная по работодателю. |
| Организация — `organization`, жёлтая | Явно названная конкретная организация. Для связи с человеком должно быть прямо указано, что это его работодатель. | Юридическая форма в названии сохраняется: `ООО «Макетный Пример»`. Из корпоративного email работодатель не достраивается. | Общее «работает в компании» не даёт конкретной организации. Ясное название без личной принадлежности сохраняется с `null`. | «Работодатель: **ООО «Макетный Пример»**»; в «работает в ООО…» предлог «в» снаружи. | «ИП Тестов Тестимир Макетович» как дополнительная организация поверх тех же Ф/И/О; «какая-то компания» как точный работодатель. |
| Паспорт — `passport`, красная | Полные явно указанные серия и номер; слово «паспорт» и предлог перед значением не включать. | Контрольная сумма/существование документа не являются ручными полями. | Не восстанавливать недостающие цифры. Владелец может быть неизвестен; красное правило сохраняется. | «Паспорт: **0000 000000**» — вымышленный суррогат серии и номера. | Только «серия 0000»; маски вместо цифр. |
| СНИЛС — `snils`, красная | Полный явно записанный номер. | Никаких обязательных ручных флагов проверки. | Не исправлять цифры по догадке и не считать частичный номер полным. | «СНИЛС: **000-000-000 00**» — суррогат формата. | `000-000-…`; только начало номера. |
| ИНН физлица — `individual_inn`, красная | Полное значение именно ИНН физлица. | ИНН организации не подменяет этот класс. | Если по контексту неясно, какой это идентификатор, не угадывать тип; кейс — на уточнение. | «ИНН физлица: **000000000000**» — суррогат. | ИНН юридического лица; фрагмент номера или текст «мой ИНН» без значения. |
| Банковская карта — `bank_card`, красная | Полный явно названный номер карты. | Не размечать счёт, БИК и последние цифры как полный номер карты. | Не достраивать номер и не определять владельца по соседству. | «Карта: **0000 0000 0000 0000**» — суррогат. | «Карта заканчивается на 0000»; номер расчётного счёта как карта. |

Возраст — `age`, жёлтая зона. Обязательно: явно названные полные годы и принадлежность либо `null`. Дополнительных полей нет. Положительный пример: «мне **37 лет**»; отрицательные: «около сорока», «30–35 лет», дата рождения. Если источник численности для возраста не подключён, сохраните сущность и пометку для уточнения; коэффициент не назначайте. Возраст не выводится из внешности, образования или стажа.

### Не являются отдельными классами разметки

| Обозначение | Что делать |
|---|---|
| ФИО | **Никогда не выделять единым спаном `fio`.** Выделить отдельные Ф/И/О и указать одного человека. Порядок слов не задаёт тип автоматически. |
| ФИ, ИО, ФО | Не выделять как спановые типы. Обработчик собирает сочетание доступных разных полных частей одного человека. |
| Местоимение | Не выделять сущность и не запускать местоименную кореференцию по «он», «его», «её» и подобным ссылкам. |
| Родство / родственник | Класс `relationship` исключён из новой разметки MVP; связи «мама», «брат» и наследование атрибутов по родству не обрабатываются. Явно написанная полная фамилия рядом остаётся сущностью фамилии, но из одного родства не следует связь с известной персоной. |
| Дата рождения | Не входит в текущую разметку; не вычислять из неё возраст. Сам явно названный возраст размечается как `age`. |

Прямая явная подпись/представление говорящего и явно названного отдельного участника допускает создание персоны. Это не разрешение цепочек местоимений или родственных связей. Персоне необязательно иметь Ф/И/О: «Посетитель А: личный телефон …» позволяет сразу создать `p_guest`. Ранее оставленные с `null` сущности позже не перепривязываются.

## Поля всего кейса

Неизвестная принадлежность — `person_id=null` у сущности; она не включает `annotation_uncertain` автоматически. Флаг отмечает необходимость уточнения ТЗ/статистики и сохраняется для прошлых шагов. Без достаточного правила неуверенность считается отсутствием алерта. Служебный контакт не даёт личного основания алерта. Прямое самоотнесение разрешено.

| Поле кейса | Обязательно | Значения и назначение | Положительный пример | Отрицательный пример |
|---|---|---|---|---|
| `case_flags.is_example` | Да | `true`, если в тексте описана учебная, техническая или вымышленная ситуация; иначе `false`. | «Рассмотрим вымышленного клиента…» → `true` на весь кейс. | Не ставить `true` только потому, что авторы датасета синтетически создали обычный диалог. |
| `case_flags.annotation_uncertain` | Да | Есть пометка для уточнения ТЗ/статистики в исходной разметке или на одном из шагов. | Ранний шаг неуверенный, позднее сработало правило: пометка сохраняется вместе с алертом. | Не назначать только из-за `person_id=null`. Без достаточного правила неуверенный шаг считается отсутствием алерта. |
| `case_flags.clarification_reason` | Да | `null` у определённого вердикта; иначе `insufficient_statistics` или `specification_gap`. `person_attribution` читается только для совместимости. | Нужен численный путь, но нет оценки населённого пункта → `insufficient_statistics`. | Не назначать причину только из-за `person_id=null`. |

Пометка `is_example` не является выключателем алерта и не присоединяет персонажей примера к реальным людям. Персоны явно отдельного примера создаются отдельно. Сработавшее правило сохраняется вместе с пометкой — затем можно изучить срабатывания модели на примерах как отдельную группу. Пример и неуверенная разметка могут сочетаться.

## Что делает LLM и что проверяет человек

Основной источник предварительной разметки — LLM по этой инструкции и минимальному формату. LLM выделяет спаны, создаёт/выбирает персоны и ставит флаги кейса; не придумывает отсутствующую статистику и не подменяет алгоритм сборки ФИО.

Человек проверяет небольшую выборку обычных кейсов и в приоритете спорные/неуверенные случаи, ошибки валидации и случаи-примеры со срабатыванием правила. Размер выборки пока не задаётся произвольным процентом. Запуск внешнего LLM API этой инструкцией не выполняется.

При проверке сначала сравнить границы и классы, затем персоны, затем флаги всего кейса и первый момент алерта. Решение человека и ссылку на пункт инструкции хранить в журнале проверки кейса, не в дополнительных полях каждой сущности. Проверка нескольких примеров полезна для отладки, но сама по себе не доказывает качество всей LLM-разметки; итоговые метрики остаются отдельной задачей.
