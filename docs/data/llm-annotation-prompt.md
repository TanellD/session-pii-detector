# Инструкция для предварительной LLM-разметки

Версия: `annotation-mvp-v2`. Использовать вместе с [таблицей классов](annotation-class-fields.md), [форматом JSON](schema.md) и [правилами алерта](annotation-guidelines.md). Ниже шаблон задания; внешний LLM API из репозитория автоматически не вызывается.

## Текст задания

Разметь предоставленную сессию по правилам `annotation-mvp-v2`. Верни только JSON с `schema_version`, `session_id`, неизменными `messages`, `entities`, `case_flags`. Не дописывай текст в сообщения и не подменяй недостающую информацию догадкой.

У каждой сущности ровно `id`, `message_id`, `start`, `end`, `type`, `person_id`. Значение равно исходному фрагменту `[start, end)`; индексы — Unicode code points. Не включай предлог перед сущностью, внешние пробелы и завершающую пунктуацию. Обозначения внутри структурированного адреса и юридическая форма внутри названия организации сохраняются по таблице классов.

Разрешённые типы: `first_name`, `last_name`, `patronymic`, `phone`, `email`, `address`, `geography`, `sex`, `age`, `occupation`, `organization`, `passport`, `snils`, `individual_inn`, `bank_card`.

Обязательные ограничения:

- **Типа `fio` нет.** Даже непрерывное полное ФИО разбей на отдельные Ф/И/О и укажи одному человеку. Не создавай типы ФИ/ИО/ФО — обработчик соберёт их сам.
- Выделяй только полные значения. Инициалы, маски и обрывки не размечай под полными типами. Полную фамилию рядом с инициалами выделить можно.
- Целиком написанные разговорные формы имени («Соня», «Тёмка») выделяй как `first_name` в исходном написании. Не восстанавливай официальную форму и не создавай дополнительный спан из догадки.
- Не достраивай имя из email, регион из телефона, пол из имени/грамматики, работодателя из домена, отчество из имени отца или фамилию из родства.
- Не размечай местоимения и родство; не разрешай местоименные и родственные цепочки. Возраст в полных годах разрешён отдельным `age`. Используй только явную принадлежность. Прямое представление говорящего допускает его отдельную персону; слово «он/его» само по себе не является основанием привязки.
- Если явно описан отдельный человек, сразу создай ему отдельный `person_id`, даже если имени ещё нет. Если связь с человеком вообще не установлена, оставь `person_id=null`. Разные `null` не обозначают одну персону.
- Прямые утверждения говорящего «мой телефон», «моя почта», «я живу…» относятся к персоне говорящего. Это допустимая явная принадлежность, а не запрещённая местоименная цепочка. Служебные/общие контакты выделяй с `person_id=null`; они не дают личного основания алерта.
- Прежние сущности не перепривязывай после позднего раскрытия владельца. Исправление добавляет новое упоминание с новыми границами; прежняя история остаётся неизменной.
- Факты разных людей не объединяй. Персона примера не присоединяется к известному человеку автоматически.
- Не делай вложенных дублей: email не содержит отдельное имя для разметки; полный адрес не дублируется вложенным городом; «ИП + Ф/И/О» не даёт дополнительного работодателя поверх того же имени.

У всего кейса заполни:

```json
{
  "is_example": false,
  "annotation_uncertain": false,
  "clarification_reason": null
}
```

`is_example=true` — когда в содержании описана вымышленная/учебная/техническая ситуация. Это не автоматическое запрещение алерта и не просто указание синтетического происхождения корпуса.

Флаг `annotation_uncertain` отмечает необходимость уточнения ТЗ/статистики. Неизвестная принадлежность уже выражена через `person_id=null` и сама по себе флаг не включает. Недостаток статистики: `insufficient_statistics`; пробел правила: `specification_gap`. Неуверенный шаг считается отсутствием алерта до достаточного правила. Пометки прошлого сохраняются и могут сочетаться с поздним алертом. Если пометок нет, ставь `false` и причину `null`. Не снимай существующую пометку только из-за новых данных. `person_attribution` читается только для совместимости.

Выделяй жёлтый `age` только при явно названном возрасте в полных годах цифрами, например «37 лет». Не вычисляй его по дате рождения; не размечай этим типом интервалы и приблизительные формулировки. Возрастной статистический справочник пока не подключён.

Телефон, СНИЛС и возраст учитывай только в цифровой записи. Разделители номера и слова единицы возраста допустимы. Полностью словесную или смешанную запись чисел не выделяй этими типами и не переводи в цифры. Такое исключение само по себе не требует флага неуверенности; прежние пометки неуверенности сохраняются.

Читай приложенный машиночитаемый контекст `annotation-context-v1`, полученный из `configs/annotation-estimator-policy.json`. Это тот же конфиг, который читает обработчик. Не считай подготовленный, но ещё не подключённый справочник действующим коэффициентом. Численность и окончательный флаг достаточности статистики определяет обработчик; не подменяй отсутствующий расчёт произвольным произведением вероятностей.

Причину и момент алерта не записывай в сущности: их вычисляет обработчик. Отдельно ФИО не алертит; ФИО/пара с полным личным телефоном, email или адресом — качественное основание. Организация жёлтая и не заменяет такой оранжевый признак. Сохраняются красное правило, контактная пара телефона/email и численный порог ≤100 при принятой оценке.

## Проверка человеком

LLM — основной источник предварительных аннотаций, человек — выборочная проверка обычных кейсов и приоритетная проверка спорных случаев. Валидатор проверяет структуру и часть формальных ограничений, а не истинность принадлежности или качество всей разметки. Для проверки человеком использовать ту же таблицу классов; спорное решение и пункт ТЗ сохранять в журнале кейса, не в сущностях.
