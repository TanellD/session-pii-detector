# Генерация синтетических сессий для проверки сервиса

Версия: `synthetic-session-generation-v2`, 2026-11-26. Рабочий шаблон для новых наборов: объём, сценарии и сложность задаются отдельно для каждого запуска. Требования к разметке определяются [ТЗ](annotation-guidelines.md), [форматом](schema.md) и [политикой калькулятора](../../configs/annotation-estimator-policy.json). Этот документ не меняет их и не означает пересмотр принятых ADR.

Версия уточнена по [содержательному аудиту пилота](../experiments/2026-11-26-difficulty-pilot-quality-audit.md). [Прежняя версия v1](synthetic-session-generation-policy-v1.md) сохранена для истории; старые наборы не становятся соответствующими v2 автоматически. Описанные ниже требования нужно реализовать и проверить в генераторе перед новым выпуском: изменение документа само по себе не исправляет код и данные.

Цель — получать диалоги, на которых можно независимо проверить извлечение атрибутов, линковку и первый алерт. Генерировать можно вручную, через LLM или программные шаблоны. Сохраняйте фактически использованный способ: программная подстановка значений не становится независимой LLM-генерацией из-за наличия текстового промпта.

## Как задать новый набор

Скопируйте задание ниже, заполните параметры и сохраните его рядом с данными до генерации. Это описательный YAML для человека или агента; существующие генераторы не обязаны принимать его как CLI-конфиг. Поля с `null` нужно заполнить либо явно оставить неприменимыми с объяснением.

```yaml
generation_policy: synthetic-session-generation-v2
dataset_version: null
purpose: null                  # extraction | linking | alert_timing | risk_tuning | combined
session_count: null
language: ru
domains: []                     # доставка, запись, возврат, поддержка продукта и т. п.
message_roles: user_only        # другой режим требует явного описания доступного контекста
user_messages: {min: null, max: null}
people_per_session: {min: null, max: null}
generator: null                 # authored | llm | templates | mixed
seed: null                     # если поддерживается выбранным способом
value_assignment:
  mode: independent_of_outcome_difficulty_and_split
  seed: null                   # отдельное назначение значений, без кодирования порядка семейств

complexity_mix:                 # доли; сумма равна 1
  easy: null
  medium: null
  hard: null
complexity_axis: null            # ownership | extraction | alert_accumulation | combined
complexity_evidence: null        # какой доступный контекст действительно требуется для целевых решений
scenario_mix: []                # взаимоисключающие основные семейства и их количества
coverage:                      # дополнительные признаки могут пересекаться
  required: []                 # например shared_phone, correction, yellow_only
  optional: []
  excluded: []
attribute_types: []             # только поддерживаемые типы из зафиксированной версии каталога
style:                         # настройки текста не меняют правила разметки
  register: []                  # нейтральный, разговорный, деловой
  typos: null                   # none | light | targeted
  irrelevant_details: null     # low | medium | high
  facts_per_message: {min: null, max: null}

reference_coverage: null        # sufficient | mixed | missing_statistics
target_outcomes: null           # необязательные квоты: positive, negative, insufficient_statistics
split:
  mode: null                   # development_only | grouped_train_dev_test | fresh_holdout
  sizes: null
  group_by: [scenario_family, profile_family, paraphrase_parent]
  parent_datasets: []
  required_type_coverage: []    # типы, которые должны быть представлены в каждой оцениваемой части
  required_alert_bases: []      # основания алерта, проверяемые в каждой части
  minimum_examples: null        # минимумы по типам/основаниям и условиям; задаются для конкретной цели
  negative_controls: []         # недостаточное сочетание, разные владельцы, служебный контакт и т. п.
annotation_schema: annotation-mvp-v2
annotation_policy_version: null
reference_versions: []
review_plan: null               # кто проверяет, какие случаи и по каким критериям
readiness:
  structural_validation: pending
  content_review: pending
  benchmark_ready: false        # меняется только после разбора результатов обеих проверок
output_directory: null         # новый каталог внутри data/, вне git
```

Задайте основные семейства так, чтобы их количества давали размер набора. Дополнительные признаки покрытия могут встречаться вместе: их доли не обязаны складываться в единицу. Один набор может состоять только из сложных сессий, только из жёлтых сочетаний или только из контролей; универсальной обязательной пропорции нет. В отчёте должно быть ясно, для какой задачи выбран такой состав.

## Как управлять сложностью

| Уровень | Принадлежность и контекст | Развитие сессии |
|---|---|---|
| Простой | Владельцы названы явно рядом с атрибутами; минимум конкурирующих связей | Последовательное раскрытие, без исправлений и смены темы |
| Средний | Несколько владельцев, часть атрибутов упоминается в следующих сообщениях | Переключение между людьми, повторы, отдельные общие или служебные контакты |
| Сложный | Несколько правдоподобных владельцев; нужное основание находится в более раннем доступном контексте | Перемежение профилей, общий атрибут, исправление, позднее новое явное упоминание, отвлекающие сведения |

Длину, число людей и плотность фактов задавайте независимо от уровня. Длинный диалог с анкетными сообщениями не обязательно сложнее короткого с переключением владельцев. Для сложного набора выбирайте конкретные механизмы сложности из таблицы; не добавляйте все механизмы в каждую сессию.

Для среднего и сложного уровня сохраняйте конкретное обоснование: какое решение нельзя получить только из текущей реплики, какой прошлый контекст нужен и что именно усложняет задачу. Повторяемые подписи «личный телефон первого участника» и «почта второго участника» могут полностью разрешать принадлежность; такой текст нельзя считать сложным только из-за нескольких людей. Не добавляйте неоднозначность, которую действующее ТЗ не позволяет разрешать.

Сложность проверяется по выбранной оси. Если в контроле нет личных атрибутов, сложная бытовая задача не доказывает сложной линковки: для оси ownership отмечайте неприменимость или исключайте такой контроль из выводов о сложности линкера. Сравнивайте уровни также на перекрывающихся длинах; остаточную зависимость длины и числа людей от уровня указывайте в ограничениях.

Перед выпуском проведите ревью без раскрытия запланированного уровня. Используйте [промпт проверки текстов](dialogue-quality-review-prompt.md), авторский разбор и, при наличии, отдельного рецензента. Массовое расхождение требует пересмотра текстов или меток уровня. Единственная оценка LLM не является основанием автоматически переименовать уровень или признать сложность доказанной.

Сложность не меняет поддерживаемую семантику. Если по текущему ТЗ принадлежность не устанавливается, правильная метка — `null`. Сценарий, требующий неподдерживаемого разрешения местоимений или родства, можно использовать как проверку ограничения, но нельзя назначать ему уверенного владельца по скрытому авторскому замыслу.

## Какие сценарии можно комбинировать

| Семейство | Что варьировать | Что проверяется |
|---|---|---|
| Обычный запрос без личных сведений | Домен, стиль, отвлекающие числа и названия | Чистые отрицательные контроли |
| Постепенное раскрытие одного профиля | Порядок атрибутов и промежутки между ними | Накопление и момент первого алерта |
| Независимые профили | Чередование владельцев и похожие типы атрибутов | Отсутствие смешивания людей |
| Явно общий личный атрибут | Телефон или адрес и дополнительные личные сведения каждого | Список владельцев без объединения остальных профилей |
| Неизвестная принадлежность | Атрибут без владельца, затем новое явное упоминание | Сохранение старого `null` и отдельная разметка нового спана |
| Служебные контакты | Контакт службы рядом с личными сведениями | Исключение служебного контакта из личного профиля |
| Повтор и исправление | Повтор значения, изменение отдельной части имени или контакта | Раздельность упоминаний, дедупликация фактов, сохранение истории |
| Только жёлтые атрибуты | Профессия, работодатель, пол, возраст, география, части имени | Численные основания и недостаток статистики |
| Жёлтые с оранжевыми | Тип контакта, владелец и порядок раскрытия | Различие качественных сочетаний и численного правила |
| Документы и ошибки формата | Валидная/невалидная checksum, неполные и маскированные значения | Извлечение по текущему ТЗ и красное правило |
| Пересечения и контекст имени | Имя в названии, рядом с email, конструкцией «фамилия …» | Границы, типы и отсутствие вложенных дублей |

Варианты одного семейства должны отличаться не только подставленными значениями: меняйте задачу пользователя, структуру реплик, порядок раскрытия, распределение атрибутов и способ явного указания владельца. Храните связь перефразирования с исходным сценарием.

## Реалистичность и синтетические значения

У диалога есть понятная цель обращения и причины сообщать выбранные сведения. Пользователь не должен перечислять анкету ради покрытия классов. Нейтральные реплики должны поддерживать разговор, а не только увеличивать длину. Не добавляйте неестественный факт ради достижения квоты: выберите подходящий сценарий.

В режиме `user_only` каждая значимая ссылка должна интерпретироваться по доступным пользовательским сообщениям. Не требуйте от модели угадать удалённый вопрос помощника. Не помещайте в исходные реплики названия классов, ID владельцев, ожидаемый момент алерта или инструкции оценщику.

Пояснение «номер общий для нас обоих» допустимо и иногда необходимо для эталона. Повторяемые указания «не объединяйте профили», «не назначайте владельца» и подробное перечисление личных полей требуют содержательной проверки: пользователь должен решать свою задачу, а не объяснять алгоритму правильную разметку. Не удаляйте нужные признаки принадлежности ради искусственного усложнения; перепишите разговор так, чтобы они естественно следовали из задачи и допустимого по ТЗ контекста.

После подстановки значений проверьте падежи имён, согласование рода, формы возраста и непрерывность говорящего. Именительный падеж нельзя вставлять во все шаблоны. Размечайте фактически написанную форму имени, не восстанавливая её в исходном тексте. Намеренные опечатки задаются параметром style.typos и отмечаются в плане; случайная ошибка генератора не становится полезным усложнением автоматически.

По [ADR-0002](../decisions/0002-no-real-pii.md) используйте только вымышленные профили и синтетические значения. Не копируйте реальные переписки, имена вместе с контактами, профили и документы. Email задавайте в `example.invalid`; телефоны и документы создавайте контролируемыми генераторами. Checksum проверяется локально: нулевое или придуманное значение не гарантирует нужного результата. Проверку контрольной суммы нельзя выдавать за проверку существования документа.

Разнообразие форматов ограничено текущим MVP: используйте зафиксированные поддерживаемые российские телефоны; неподдерживаемые формы — только как явно запланированные контроли. Типы берите из [каталога классов](../../configs/annotation-classes.json), а правила границ — из [таблицы полей](annotation-class-fields.md). Исключённые из MVP категории не возвращаются в эталон через настройки сложности.

### Независимое назначение значений

Числовые части телефона, email, документов, адресов и названий организаций не должны кодировать класс алерта, уровень сложности, часть набора или порядковый индекс семейства. Запрещены разные диапазоны для положительных и отрицательных сценариев и последовательное назначение значений по плану, в котором исходы сгруппированы. Простое перемешивание готовых сессий эту зависимость не устраняет.

Назначайте значения отдельным случайным или проверенным независимым от этих признаков механизмом. Фиксированный seed допустим и сохраняется; он не должен выбирать специальный диапазон для класса или части. Общие контакты, повторы и исправления создаются по смыслу сценария внутри соответствующих групп; требование независимости не отменяет намеренного совпадения общего атрибута. Контрольная сумма и допустимость формата сохраняют смысл по ТЗ: это целевые признаки, а не побочные коды.

Перед выпуском сопоставьте распределения подстрок, диапазонов, префиксов и форматов между исходами, сложностями и частями. Проверьте, нет ли способа угадывать метку по произвольному коду генератора. Случайное назначение и успешная проверка уникальности сами по себе не доказывают отсутствие смещения. Обнаруженная искусственная зависимость блокирует признание набора benchmark до исправления и повторной проверки; результаты поиска и его ограничения сохраняются.

## Как получать эталон

1. Составьте план сценария: цель обращения, вымышленные профили, предполагаемые атрибуты и порядок раскрытия. Число людей в плане — авторские метаданные, а не подсказка модели.
2. Напишите сообщения, затем разметьте все действительно присутствующие поддерживаемые атрибуты. Если текст отклонился от плана, исправьте план или текст и повторно проверьте разметку; не игнорируйте незапланированную сущность.
3. Проверьте границы, типы и владельцев по доступному префиксу. Один известный владелец — строка, несколько явно известных — список, неизвестный — `null`. Не считайте все `null` одним человеком. Позднее уточнение не переписывает старый спан.
4. Подтвердите необходимые признаки для калькулятора отдельно: например, тип жилья, личное использование контакта, однозначную профессиональную группу. Укажите основание подтверждения; не расширяйте минимальную схему сущностей произвольными полями.
5. Получите первый алерт существующим калькулятором по каждому префиксу. Сохраните причину, опорные упоминания, оценки и версии справочников. Порядок причин и обработка неопределённости определяются ТЗ. Веса сервиса и его предсказания не участвуют в получении эталона.
6. Проведите независимую проверку по заданному плану. Авторская или LLM-разметка до этой проверки остаётся предварительной. Повторная разметка той же моделью по тому же промпту не считается независимым подтверждением.

Для запуска и контрактов используйте [инструкцию разметки](annotation-workflow.md). Общий инструмент проверки сессии — `python -X utf8 tools/annotation_contract.py --input <путь-к-аннотации.json>` из корня репозитория, с подготовленными справочниками. Режим `--policy-only` не заменяет полный численный расчёт. Корпусные оболочки, включая `snapshot.json`, требуют отдельного прохода по аннотациям сессий; указанная команда проверяет одну аннотацию, не произвольный корпусный файл.

Для численных положительных сценариев заранее выбирайте сочетания, для которых есть применимые проверенные справочники. Вымышленному городу нельзя назначать население произвольно; частоты профессии, пола, возраста и территории нельзя независимо перемножать. Синтетические численные фикстуры для проверки границы правила маркируйте и оценивайте отдельно от реалистичных диалогов. Подтверждение квартиры автором сценария — явное допущение, а не результат геокодирования.

Если достаточного основания нет и статистика недоступна, сохраняйте `annotation_uncertain` и причину по ТЗ. Это отдельный разрез отчёта. Различайте отрицательные контроли без неопределённости на проверяемом шаге и отсутствие алерта из-за нехватки статистики. Не исправляйте метки, чтобы выполнить желаемую долю положительных: измените план ещё не зафиксированной генерации либо отчитайте фактический состав.

## Разделение и доступ модели

Назначьте части набора до подбора весов, порогов и промптов. Варианты общего шаблона, профиля и перефразирования должны оставаться в одной части. Практически это группы связности: если сессии имеют общий шаблон или профиль или родительский диалог, их нельзя разделить между train и test. Если все сессии связаны общими профилями, для независимого test нужно сгенерировать новые семейства профилей и сценариев, а не просто перемешать ID.

До назначения частей заполните требования к покрытию под цель оценки. Каждый тип и основание, для которых планируется отдельный вывод о качестве или весе, должны иметь достаточные для выбранной цели примеры в соответствующих train, validation и test. Минимумы задайте заранее; универсального количества для всех задач нет. Если одновременно выполнить группировку и покрытие нельзя, добавьте новые независимые семейства, пересмотрите размер или явно сузьте назначение набора.

Для типов и сочетаний включайте применимые положительные и отрицательные контроли: разные владельцы, неполные значения, неподходящее сочетание, служебные контакты. Схожие контрольные пары сохраняются в одной группе разделения. Для person и неопределённой принадлежности нужны собственные случаи, если их поведение входит в задачу. Неуверенные отрицательные метки из-за отсутствия статистики не заменяют однозначные отрицательные контроли.

Выпустите таблицу покрытия «тип/основание × часть × сложность» с числом сессий и упоминаний, исходами и неопределённостью. Отсутствующий тип означает отсутствие соответствующей проверки, а не нулевую ошибку. Например, нельзя подтверждать вес работодателя на test без работодателей. Исследовательский набор с неполным покрытием допустим с явно ограниченной областью выводов, но не как общий benchmark сервиса.

Для диагностического набора допустима одна development-часть. Для свежего отложенного теста используйте новые семейства и профили, не просмотренные при настройке. Сохраняйте родителей и повторно использованные материалы, включая основу Андрея, если они применялись. Набор с пересекающимися семействами можно оценить как отдельный диагностический срез, но не называть проверкой на новых семействах.

Модель получает только сообщения и состояние, доступные сервису на данном шаге. Не передавайте ей сценарный план, истинное число людей, ожидаемые классы текущей реплики, эталонных владельцев или будущие сообщения. Список уже найденных сервисом людей допустим; истинный список из авторского плана — нет. При изолированной проверке линкера эталонные спаны допустимы только как явно обозначенный режим; такой результат не является качеством полного сервиса с реальным NER.

## Что сохранять и проверять перед оценкой

В новом каталоге внутри `data/` сохраните задание и фактический промпт, план сценариев, исходные сообщения, аннотации, расчёты по префиксам, результаты ревью, разбиение и манифест. Названия файлов могут соответствовать существующему генератору; их назначение должно быть описано. В манифесте укажите способ генерации, версии данных и политики, хеши кода и справочников, источник исходных материалов и ограничения. Для LLM дополнительно сохраните модель, параметры, исходные ответы и ручные исправления. Секреты остаются в `.env`.

Перед заморозкой проверьте соответствие схеме и границам, ID и владельцев, форматы и checksum, служебные контакты, фактический состав сценариев, дубли текстов и шаблонов, пересечение групп между частями и согласованность префиксных алертов. Недостаток статистики должен оставаться видимым в отчёте. Все неоднозначные случаи из плана ревью должны получить решение либо явную отметку, что ревью не завершено.

### Условия допуска к расширению и benchmark

Структурная проверка и содержательное ревью имеют отдельные результаты. Для каждого пункта сохраняйте проверяющего, свидетельства, команду получения чисел и решение:

| Проверка | Условие готовности |
|---|---|
| Контракт и эталон | Границы, владельцы, checksum и префиксные алерты проверены на конечных текстах |
| Побочные признаки | Нет неразобранной искусственной зависимости значений и форматов от исхода или части |
| Логика и язык | Нет существенных неразобранных противоречий, скрытого контекста, ошибок согласования и подсказок оценщику |
| Сложность | Есть обоснование по выбранной оси и разбор расхождений слепого ревью с планом |
| Покрытие и разделение | Выполнены заранее заданные минимумы; группы не пересекаются; сходные межчастные тексты разобраны |
| Неопределённость | Недостаток статистики и неизвестная принадлежность сохранены и отчётливо отделены от однозначных контролей |

Успешный калькулятор или verdict=pass от LLM закрывают только свою часть проверки. Извлечённая из текста цитата подтверждает наличие фразы, но не правильность объяснения рецензента. Спорные замечания требуют авторского разбора с сохранением исходного ответа. Проверку, выполненную автором генерации, нельзя называть независимым ревью.

Пока существенные проблемы остаются, сохраняйте benchmark_ready=false и назначение «диагностика/ревью». Исправлять и проверять пилот можно; расширять корпус с тем же выявленным дефектом или публиковать подтверждающие метрики по нему нельзя. Для готового набора указывайте, какие задачи и типы покрыты и какие ограничения сохраняются; флаг готовности не является обещанием качества в реальном трафике.

После заморозки исправление создаёт новую версию эталона с сохранением предыдущей и перечнем различий. Оно не должно незаметно менять вход уже идущего модельного прогона. Данные не коммитьте в git; описание эксперимента, команды проверки и генератор сохраняйте в репозитории. Численные результаты публикуйте с воспроизводимой командой по [протоколу метрик](../kb/metrics.md).

## Задание для повторного использования

> Создай синтетический набор по приложенному заполненному заданию и политике `synthetic-session-generation-v2`. До генерации задай требования к покрытию частей и сгруппируй связанные сценарии и профили. Назначай значения независимо от исхода, сложности, части и порядка семейств; сохраняй необходимые общие атрибуты и повторы. Напиши естественные сообщения без инструкций оценщику, проверь падежи, род, формы возраста и говорящего. Обоснуй сложность требуемым контекстом, а не длиной. Разметь конечные тексты по зафиксированному ТЗ, рассчитай алерты калькулятором без весов сервиса и без выдуманной статистики. Сохрани происхождение, неопределённость, таблицу покрытия, результаты структурной проверки и содержательного ревью отдельно. Проверь побочные коды и сходство частей. При существенных неразобранных проблемах оставь benchmark_ready=false и сначала исправь пилот; не расширяй дефектный генератор. План и эталон модели не передавай. Используй новый каталог; существующие наборы и ТЗ не переписывай.

Для отдельного запуска достаточно приложить заполненный YAML и назвать выбранные сценарии. Старые [пилотный промпт](session-alerts-generation-prompt.md) и [разговорные заготовки](user-only-synthetic-sessions.md) можно использовать как материал для сценариев; ограничения конкретного пилота не становятся обязательными для всех новых наборов.

Готовый набор для знакомства со сценарием: [по три примера каждого семейства средней сложности](../experiments/2026-11-26-medium-scenario-examples.md). Страница описывает расположение текстов и разметки вне git и команду повторной сборки.

Пример заранее разделённого набора: [авторский пилот трёх сложностей с train/validation/test](../experiments/2026-11-26-difficulty-pilot-90.md). Его [аудит выявил проблемы](../experiments/2026-11-26-difficulty-pilot-quality-audit.md): пилот не является примером соответствия v2 и не готов к подтверждающей оценке. Он сохраняется для разбора ошибок генерации.
