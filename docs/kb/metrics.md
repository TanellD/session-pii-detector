# Метрики качества сессионной детекции ПДн

Статус: протокол первой версии для ревью в PR #19, подготовленный по обсуждению
с лидом 08.11.2026. Численные цели и результаты baseline пока не определены.
Основная метрика — F2-timely; F2-session, offset и FP0 — диагностика сервиса.

Основания: [протокол первого алерта](https://github.com/TanellD/session-pii-detector/pull/19#issuecomment-6630424424),
[разбор ошибок компонентов](https://github.com/TanellD/session-pii-detector/pull/19#discussion_r4506696250),
[вычисляемый скор](https://github.com/TanellD/session-pii-detector/pull/19#discussion_r4506671723).
Уточнения не означают утверждения всего протокола командой.

Связано: [открытые вопросы](../project/metrics-open-questions.md),
[задержка](latency-budget.md), [проект ТЗ на разметку](../data/metrics-annotation-requirements.md).

## Общие правила

- Сессии разделяются по `session_id`; роли и нумерация сообщений фиксируются
  конфигурацией корпуса.
- `t_gold` — первое сообщение, на котором по эталонной политике требуется алерт.
  Учитываются только текущее сообщение и предыдущий контекст.
- `t_pred` — сообщение первого алерта; предупреждение алертом не считается.
  При блокирующем применении решение принимается до передачи сообщения дальше.
- Положительная сессия имеет `t_gold`; отрицательная не требует алерта на всём
  протяжении. Последующие исправления не отменяют исторический `t_gold`.
- Пока оценивается первый момент; дополнительные положительные моменты
  отмечаются флагом без обязательного указания позиций и не меняют эту оценку.
- Если неуверенность мешает определить наличие утечки или первый момент,
  сессия получает `unknown`, исключается из основных сессионных метрик и
  учитывается отдельно: число, доля, причины. Неуверенность в частном атрибуте
  не исключает сессию автоматически, если эталон алерта ясен.
- Micro: суммируем исходы по корпусу, затем считаем метрику.
  Macro: среднее определённых метрик заранее заданных групп с отчётом покрытия.
- Ниже определён протокол оценки; конкретные основания алерта должны быть
  согласованы и версионированы с данными, а не выведены из ответов оцениваемой системы.

## 1. F2-session: обнаружение утечки

Единица — сессия; агрегация — micro.

| Эталон | Предсказание | Исход |
|---|---|---|
| Есть утечка | Есть алерт независимо от позиции | TP |
| Есть утечка | Нет алерта | FN |
| Нет утечки | Есть алерт | FP |
| Нет утечки | Нет алерта | TN |

`Precision = TP / (TP + FP)`

`Recall = TP / (TP + FN)`

`F2-session = 5TP / (5TP + 4FN + FP)`

Precision — доля обоснованных алертов; Recall — доля обнаруженных положительных
сессий. F2 придаёт больший вес полноте. Ранний и поздний алерты положительной
сессии здесь дают TP: положение оценивается отдельно.

## 2. F2-timely: своевременность первого алерта

Единица — первое целевое событие сессии; агрегация — micro.
Допуска на раннее или позднее срабатывание нет.

| Случай | Вклад |
|---|---|
| Положительная сессия, `t_pred = t_gold` | TP |
| Положительная сессия, `t_pred < t_gold` | Только FP |
| Положительная сессия, `t_pred > t_gold` | FN |
| Положительная сессия, алерта нет | FN |
| Отрицательная сессия, есть алерт | FP |
| Отрицательная сессия, алерта нет | Нет вклада в TP/FP/FN |

`F2-timely = 5TP / (5TP + 4FN + FP)`

Precision и Recall при необходимости вычисляются из этих же счётчиков.
Ранний первый алерт означает необоснованную остановку и даёт только FP,
без дополнительного FN. Поздний или отсутствующий алерт даёт FN.
Каждая сессия вносит не более одного исхода в TP/FP/FN этой метрики.
Последующий точный алерт не исправляет ранний первый.
Это специальный протокол оценки первого момента; его счётчики отличаются
от F2-session. В частности, Recall-timely = TP / (TP + FN) не включает ранние
алерты в знаменатель: они снижают Precision и F2 через FP. Поэтому Recall-timely
нельзя интерпретировать как долю точных попаданий среди всех положительных сессий.

## 3. Расстояние до триггера

Считается на TP **F2-session**, где есть и эталонный, и предсказанный момент:

`offset_s = t_pred_s - t_gold_s`

Отрицательное значение — ранний алерт; ноль — точный; положительное — поздний.

`exact_rate = count(offset = 0) / count(TP_session)`

Аналогично считаются доли ранних и поздних срабатываний. Публикуются медиана,
p95 и максимум `abs(offset)`, распределение знакового offset и число наблюдений.
Пропуски алерта не имеют offset и показываются как FN-session.
На TP-timely расстояние не оценивается: там оно всегда нулевое.
Это расстояние в сообщениях, не время обработки.

## 4. FP0

`FP0 = FP_negative / N_negative`

Числитель — отрицательные сессии с алертом, знаменатель — все уверенно
отрицательные сессии. Меньше — лучше. Отрицательная сессия может содержать
отдельные атрибуты, не требующие алерта по эталонной политике.
Ранние алерты положительных сессий в FP0 не входят.

## 5. Извлечение

Единица — спан с границами и типом; агрегация — micro.
TP: exact match, type-aware. Матчинг взаимно однозначный: один эталон
и одно предсказание дают максимум один TP. Дубли и несовпавшие предсказания —
FP, несопоставленные эталоны — FN. Неверные границы или тип обычно дают FP и FN.

`P_ext = TP_ext / (TP_ext + FP_ext)`

`R_ext = TP_ext / (TP_ext + FN_ext)`

`F2_ext = 5TP_ext / (5TP_ext + 4FN_ext + FP_ext)`

Сообщения без упоминаний включаются для учёта FP. Правила вложенности и
нормализации фиксируются версией разметки до запуска.
Дополнительная диагностика — разрезы по типам атрибутов.

## 6. Принадлежность атрибутов людям

Человек представлен локальным ID. Номера между предсказанием и эталоном
могут различаться. Проверяется группировка атрибутов по владельцам, а не
только кореференция текстовых упоминаний.

Для изолированной оценки подаются эталонные атрибуты с устойчивыми ID.
Единица первой версии — упоминание атрибута; переход к дедуплицированным
фактам требует отдельного протокола. Пары между сессиями не образуются.

### Pairwise Precision / Recall

Предлагаемое правило первой версии: два различных атрибута связаны,
если у них есть хотя бы один общий известный владелец.
Оно допускает несколько владельцев одного атрибута.

- TP: пара связана в эталоне и предсказании.
- FP: связана только в предсказании — ошибочное объединение.
- FN: связана только в эталоне — ошибочное разделение.

`P_pair = TP_pair / (TP_pair + FP_pair)`

`R_pair = TP_pair / (TP_pair + FN_pair)`

`F1_pair = 2TP_pair / (2TP_pair + FP_pair + FN_pair)`

Счётчики суммируются по сессиям. Правило требуется сверить на данных:
оно не различает число общих владельцев и не заменяет полноценную оценку
связей «атрибут → человек».

### B-cubed как альтернативная диагностика

Обычный вариант требует одинакового набора элементов и ровно одного
владельца каждого элемента с обеих сторон.
Для атрибута `m`: `C(m)` — предсказанная группа, `G(m)` — эталонная.

`P_m = |C(m) ∩ G(m)| / |C(m)|`

`R_m = |C(m) ∩ G(m)| / |G(m)|`

`P_B3 = mean_m(P_m)`; `R_B3 = mean_m(R_m)`

`F1_B3 = 2 P_B3 R_B3 / (P_B3 + R_B3)`

Precision — чистота группы типичного атрибута; Recall — полнота сбора
атрибутов того же человека. B-cubed полезна при сильно различающихся размерах
групп: pairwise даёт большим группам квадратичный вес через число пар,
B-cubed усредняет по элементам. Она учитывает одиночные группы; при их
преобладании нужен дополнительный разрез людей с повторными упоминаниями.

Источник: [описание реализации B-cubed](https://cogcomp.seas.upenn.edu/software/doc/lbjcoref/edu/illinois/cs/cogcomp/lbj/coref/scorers/BCubedScorer.html).

Для общих атрибутов обычные формулы неприменимы без адаптации.
Возможен однозначный срез с отчётом покрытия, но если срез зависит от
предсказаний, его нельзя использовать для самостоятельного ранжирования систем.
Полная оценка пересекающихся групп — открытый вопрос.

### Неизвестные владельцы и шаг оценки

«Неопределённо» — служебная группа, не утверждение единого человека.
Эталонные атрибуты с неизвестным владельцем исключаются из оценки
принадлежности с отчётом количества. Предсказанное «неопределённо» не
создаёт положительных пар: для известной эталонной пары такое воздержание даёт FN.
Отдельная политика алерта и повышенный порог служебной группы — гипотезы.

Предлагается оценивать состояние после каждого сообщения на доступном
префиксе; итоговое состояние показывать дополнительно. При суммировании
по шагам старые пары учитываются повторно. Выбор агрегации и веса длинных
сессий остаётся открытым; до сравнения систем его нужно зафиксировать.

## 7. Экспериментальная CPE Match Rate

Не входит в обязательные критерии приёмки. До определения формулы и допуска
статус — «не рассчитывается», а не ноль.

Разметчики указывают типы и принадлежность атрибутов; числовой эталон
`c_gold` вычисляется по выбранной формуле.

`CPE_match = count(|c_pred - c_gold| <= epsilon) / N_evaluated`

Отдельно показываются доли завышения и занижения за пределами допуска.
Это абсолютный допуск; относительный требует отдельного правила для нулевого эталона.
Уровень скора (человек/сессия), шаг и формула пока не определены.

Изолированная проверка получает правильные атрибуты и принадлежность.
Она проверяет вычисление формулы, но не обосновывает веса или порог.
Качество политики проверяется по независимому эталону необходимости алерта.

## 8. Пустые знаменатели

- Нулевой знаменатель — `N/A` с причиной.
- F2 считается напрямую по счётчикам. Если положительные есть и все пропущены,
  F2 равна нулю даже при неопределённой Precision.
- Нет отрицательных сессий — FP0 `N/A`; нет TP-session — offset `N/A`.
- Нет оцениваемых элементов — B-cubed `N/A`. Если определённые P и R обе
  равны нулю, F1 принимается равной нулю; неопределённый компонент даёт F1 `N/A`.
- Macro F2 — среднее определённых F2 по заранее заданным типам сессий;
  исключённые группы и причины публикуются.

## 9. Отчёт

Обязательны: версии данных и разметки, commit сервиса и оценщика, конфигурация
политики, команда воспроизведения, размеры выборки, unknown, исключения,
исходные счётчики и знаменатели, значения и причины `N/A`.
Для частей сервиса — эталонные или предсказанные входы, шаг оценки и покрытие.
Метод квантилей фиксируется конфигурацией.

Необоснованные цели прежнего черновика не являются требованиями.
После baseline согласуются уровни «требует улучшения», «приемлемо»,
«очень хорошо». Сам baseline не доказывает приемлемость результата.
Измерения оформляются по шаблону `docs/experiments/`; каждое измеренное число
сопровождается командой из репозитория.
