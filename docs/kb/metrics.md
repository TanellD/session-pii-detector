# Метрики качества детекции ПДн

Этот документ описывает метрики, которыми измеряется качество модуля детекции персональных данных (ПДн) и триггера утечек. Из постановки задачи уже известно, что:
- точность необходимо определять по сессиям;
- нужно учитывать задержку в сообщениях;
- время обработки нового сообщения укладывается в бюджет латенси по мере роста сессии.

Для каждой метрики зафиксированы:
- **уровень единицы анализа** (что считается один раз: сообщение, сессия, спан, сущность);
- **способ агрегации** (micro / macro, если применимо);
- **определения TP / FP / FN** — чтобы метрика была однозначной и сравнимой между запусками.

Главная метрика — **micro F2**. Остальные — вспомогательные: они объясняют, *почему* главная метрика имеет такое значение, и помогают локализовать проблемы.

---

## 0. Термины и уровни

| Термин | Определение |
|---|---|
| **Сообщение (message)** | Одна единица переписки (одно сообщение в сессии). |
| **Сессия (session)** | Набор сообщений, объединённых одним пользователем. |
| **Спан (span / упоминание)** | Непрерывный фрагмент текста, помеченный как ПДн определённого типа (имя, телефон, email и т.д.). |
| **Сущность (entity)** | Один объект реального мира (конкретный человек, номер, email). У одной сущности может быть несколько упоминаний в разных сообщениях. |
| **Корпус (corpus)** | Все сессии тестовой выборки вместе. |
| **Триггер** | Событие/сообщение, после которого модуль должен поднять алерт об утечке ПДн. |

**Уровень единицы** — что считается один раз (сессия, спан, сущность).
**Агрегация** — как результаты по единицам сводятся в одно число (micro — суммируем TP/FP/FN по всем единицам; macro — усредняем метрику по группам без учёта размера).

---

## 1. micro F2 (главная)

**Уровень единицы:** сессия.
**Агрегация:** corpus-level (micro) — TP/FP/FN суммируются по всем сессиям корпуса, метрика считается один раз.

**Что измеряет:** был ли в сессии вычислен модулем триггер и поднят ли модуль соответственно алерт по нему, как только он появился. Иными словами — насколько хорошо модуль определяет *наличие утечки в сессии* и *своевременность* алерта.

### Определения TP / FP / FN (на уровне сессии)

- **TP** — сессия, в которой утечка ПДн есть (по эталону), модуль вычислил триггер и поднял алерт, расстояние до триггера допустимое.
- **FP** — сессия, в которой утечки нет (по эталону), но модуль поднял алерт.
- **FN** — сессия, в которой утечка есть (по эталону), но модуль не поднял алерт (триггер не вычислен или алерт не вызван).

### Формулы

>* **Precision** = TP / (TP + FP)
>* **Recall** = TP / (TP + FN)
>* **F2** = 5 * (Precision * Recall) / (4 * Precision + Recall)

Диапазон F2 — от 0 до 1; стремимся к 1. Вес β = 2 означает, что **Recall для нас важнее Precision**: пропуск утечки (FN) штрафуется сильнее, чем ложный алерт (FP).

### Почему micro, а не macro

Micro даёт устойчивую оценку на всём корпусе и не позволяет крошечным группам сессий непропорционально влиять на результат. Macro F2 по типам сессий можно считать как **диагностику** (см. раздел 7), но главная метрика — micro.

### Что фиксируется в отчёте

- TP / FP / FN в абсолютных числах (чтобы была видна база).
- Precision, Recall, F2.
- Отдельно — число сессий без ПДн (знаменатель для FPR, см. раздел 3).

## 2. Расстояние до триггера (вспомогательная)

**Уровень единицы:** сессия.
**Агрегация:** распределение по сессиям (медиана, p95, max) + доля точных попаданий.

**Что измеряет:** на том ли сообщении обнаруживается триггер и вызывается алерт.
Измеряется **расстояние в сообщениях** (не во времени) между сообщением-триггером
по эталону и сообщением, на котором модуль вызвал алерт.

⚠️ Это **не latency**. Время отклика здесь не измеряется. Метрика отвечает на вопрос «насколько точно определена позиция триггера», а не «как быстро сработал алерт».

### Определения

Для каждой сессии с утечкой (TP из раздела 1):

- **offset = позиция_алерта − позиция_эталонного_триггера** — расстояние до эталона. Знак показывает нам, поторопились ли мы или опоздали.
- **offset = 0** — алерт вызван на том же сообщении, что и эталонный триггер (точное попадание).

### Агрегация

- Доля сессий с `offset = 0` (точность позиции).
- Медиана и p95 абсолютного offset по сессиям с утечкой.
- Максимальный offset (худший случай).

## 3. FPR / FP0 (вспомогательная) [S18]

**Уровень единицы:** сессия (документ).
**Агрегация:** corpus-level.

**Что измеряет:** долю **ложных срабатываний** — некорректно вызванных алертов
на сессиях, где совокупной утечки ПДн (СУП) нет.

### Определения

- **FP** — сессия, где утечки нет, но модуль поднял алерт.
- **N (negatives)** — общее число сессий без ПДн в корпусе.

### Формула

>* **FPR (FP0)** = FP / N

Знаменатель — **только сессии без СУП**. Сессии с реальной утечкой в знаменатель
не входят, поэтому метрика показывает «цену ложной тревоги» на чистых данных,
а не общую долю ошибок.

### Целевой порог

Задаём отдельно (например, `FP0 ≤ 1%`). Порог фиксируется в этом документе и
не меняется между запусками без явного решения команды.

## 4. Extraction Quality (Precision / Recall / F2)

**Уровень единицы:** спан (упоминание).
**Агрегация:** micro по корпусу; macro по типам сущностей — как диагностика.

**Что измеряет:** правильно ли выделены упоминания ПДн — найдены ли нужные
фрагменты, с правильными границами и правильным типом.

### Правило матчинга (фиксируется и не меняется между запусками)

- **Exact match, type-aware**: предсказанный спан засчитывается как TP, только
  если его границы и тип совпадают с эталонным.
- Каждый эталонный спан даёт **не более одного TP**. Если система выдала несколько
  предсказаний на один эталон, TP получает только одно (лучшее), остальные — FP.
- Вложенные и пересекающиеся спаны обрабатываются по тому же правилу: один
  эталон — максимум один TP.

### Определения TP / FP / FN

- **TP** — предсказанный спан, совпавший с эталонным по правилу матчинга.
- **FP** — предсказанный спан, не совпавший ни с одним эталонным (лишнее извлечение).
- **FN** — эталонный спан, не совпавший ни с одним предсказанным (пропуск).

### Формулы

>* **Precision** = TP / (TP + FP)
>* **Recall** = TP / (TP + FN)
>* **F2** = 5 * (Precision * Recall) / (4 * Precision + Recall)

### Важно

- Сообщения без ПДн участвуют в подсчёте FP (если система что-то нашла), но не
  дают TP/FN. Их включать обязательно, иначе Precision завышается.
- Нормализация границ (пробелы, кавычки, инициалы) должна быть описана явно.
  Если нормализация применяется — она применяется и к эталону, и к предсказанию.

## 5. Entity Linking Quality

**Уровень единицы:** сущность / кластер упоминаний.
**Агрегация:** pairwise precision/recall по кластерам; при необходимости — B-cubed.

**Что измеряет:** правильно ли упоминания склеены в одну сущность. Одна сущность
может быть «размазана» по нескольким сообщениям; метрика проверяет, что упоминания
одного реального объекта попали в один кластер, а разные объекты не склеены.

### Определения (pairwise)

Рассматриваются пары упоминаний:

- **TP** — пара упоминаний, которая в эталоне относится к одной сущности, и в
  предсказании тоже отнесена к одной сущности.
- **FP** — пара, которая в предсказании в одной сущности, а в эталоне — к разным
  (ошибочная склейка).
- **FN** — пара, которая в эталоне в одной сущности, а в предсказании — к разным
  (разрыв одной сущности на несколько).

### Формулы

>* **Pairwise Precision** = TP / (TP + FP)
>* **Pairwise Recall** = TP / (TP + FN)

F-меру по pairwise можно считать, но нагляднее на данный момент смотреть на обе метрики
отдельно: склейка лишнего (покажет низкий Precision) и разрыв своего (низкий Recall) —
это разные типы ошибок с разными последствиями и разными способами улучшения.

### Важно

Правило кореференции (какие упоминания считаются одной сущностью) должно быть
зафиксировано. Без него TP/FP/FN «плывут», и метрика несравнима между запусками.

## 6. CPE Match Rate

**Уровень единицы:** сессия.
**Агрегация:** corpus-level.

**Что измеряет:** корректно ли накоплен score по сессии (Cumulative PII Exposure) [S17] —
то есть правильно ли агрегированы результаты извлечения и линковки в итоговую
оценку экспозиции ПДн по сессии.

 - Это метрика **агрегации**, а не извлечения и не линковки. Ошибки извлечения и линковки измеряются в разделах 4 и 5; здесь проверяется, что итоговый score посчитан верно при условии корректных входных данных.

### Определения

Для каждой сессии сравнивается предсказанный CPE-score с эталонным:

- **TP** — сессия, где накопленный score совпал с эталонным (необходимо определить пороговое значение и диапазон отклонений, которые мы согласны принять).
- **FP** — сессия, где score завышен относительно эталона (ложная тревога).
- **FN** — сессия, где score занижен относительно эталона (пропустили СУП).

### Формулы

>* **Accuracy** = TP / (TP + FP + FN)

Если мы хотим отдельно контролировать завышение или занижение score, необходимо отдельно вести отчет по FP и FN.

### Важно

CPE Aggregation Accuracy **не заменяет** Extraction Quality и Entity Linking
Quality. Она отвечает на вопрос «правильно ли посчитан итог», а не «правильно ли
извлечены и склеены данные». При разборе ошибок сначала смотрим разделы 4 и 5,
затем — раздел 6.

---

## 7. Диагностика: возможные дополнительный macro-разрезы

Для локализации проблем можно также считать следующие метрики:

- **macro F2 по типам сессий** — показывает, не проваливается ли модуль на редких
  типах сессий (при этом главной остаётся micro F2 из раздела 1).
- **Extraction Quality по типам сущностей** (имена, телефоны, email и т.д.) —
  показывает, какие типы ПДн извлекаются хуже.
- **Entity Linking Quality по типам сущностей** — показывает, где чаще рвутся или
  склеиваются лишние элементы сущностей.

## 9. Что фиксируется в отчёте о запуске

Чтобы метрики были сравнимы между запусками, в отчёт включаются:

1. Абсолютные TP / FP / FN для каждой метрики (не только производные значения).
2. Размер выборки: число сессий, сообщений, спанов, сущностей; отдельно — число
   сессий без ПДн (знаменатель FPR).
3. Правило матчинга для Extraction Quality (exact match, type-aware) и правило
   кореференции для Entity Linking Quality.
4. Целевые пороги (например, `micro F2 ≥ X`, `FPR ≤ Y`), зафиксированные до запуска.
