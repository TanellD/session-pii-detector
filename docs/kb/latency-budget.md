# 1. Бюджет латенси
- **Перцептивный бюджет**: Наш модуль не должен увеличивать TTFT более чем на 20% (нужно обсудить; потенциальная верхняя граница — 30%), потому что прирост в этом диапазоне еще не ощущается пользователем как ухудшение.
Если базовая TTFT модели уже находится в диапазоне 150–200 мс, то добавка в 20% (30–40 мс) с высокой вероятностью останется ниже порога заметности. Если базовая TTFT выше, 20% может дать абсолютную добавку, которую пользователь заметит, но она будет восприниматься как «небольшое замедление», а не как «зависание» [S20, S21].
- **Инженерный бюджет**: совокупная latency (TTFT модели + модуль) P95 ≤ _целевое значение_ мс, где P95 модуля ≤ _целевое значение_ мс, не растёт с длиной сессии.

Таким образом, для нас допустимы следующие методы:
* rule-based проверки, чистые регулярные выражения (regex). Добавляют ~0.003 мс (p50) [S19].
* Regex + энтропийный анализ: ~0.006 мс (p50) [S19].
* лёгкий NER (например, GLiNER или spaCy) ~5.5 мс (p50). Но при масштабировании на длинный текст (5300 символов) задержка может вырасти до >500 мс! [S19]
* операции с накопленным состоянием в памяти / быстром кэше.

Запрещены:
* Вызов внешней LLM для классификации каждого сообщения.
* Перечитывание всей истории сессии с нуля.
* Полный повторный парсинг всех предыдущих сообщений.

# 2. Архитектурное требование: O(1) доступ к состоянию
Состояние сессии хранится как агрегированная структура (entity registry / graph), обновляемая инкрементально. Время обработки нового сообщения не должно зависеть от количества предыдущих сообщений.

* **Паттерн**: накапливание сигналов и обновление score/графа с сущностями инкрементально, а не пересчитывание всего заново. Аналогичный подход используется в CAMP [S17] и в Entity-Aware Evidence Accumulation [S22].

3. Методика замера
3.1. Что замеряем
Для каждого сообщения в сессии:
1) t_start — момент входа сообщения в модуль.
2) t_end — момент, когда модуль вернул решение (выялены ПДн, залинкованы сущности, обновлен score).
3) latency = t_end − t_start (в миллисекундах).

Замеры проводятся в изоляции от потенциальных сетевых задержек LLM.

3.2. Тестовые сессии
Сформировать набор сессий разной длины (10, 50, 100, 200 сообщений), и для каждой длины провести тестовые прогоны. Поскольку мы не обрабатываем историю диалога заново и храним только состояние по score, latency не должна расти.

3.3. Расчёт метрик
Для каждого сообщения во всех сессиях собрать latency. Рассчитать P50 (медиана), P95, P99, Max.
**Критерий прохождения**: P95 ≤ _целевое значение_ мс на всех длинах сессий.
**Дополнительно**: сравнить P95 latency для сессий длины 10 и длины 200. Разница не должна превышать _целевое значение_ мс (или _целевое значение_ от бюджета).
