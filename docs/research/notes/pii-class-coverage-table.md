## Назначение документа

Свести в одну таблицу, что реально проверено по каждой из 14 групп признаков
и по каждому из 7 подпунктов специального флага (ст. 10), и разделить результат
на три категории:

- **A** — можно взять как есть: достаточно отображения метки; подтвердить на данных.
- **B** — нужна дополнительная логика: разбор/нормализация, regex, checksum,
  разрешение конфликтов, смена меток/настроек.
- **C** — не реализуемо в текущем подходе/данных: с причинами и границами вывода.
  Это ограничение текущего решения, а не доказательство невозможности класса.

Документ **не** утверждает готовность MVP. Один TP не означает, что класс готов.
`SPECIAL_CATEGORY` — упоминание сигнала, не юридический вывод. Checksum/Luhn/формат
не подтверждают реальность или выдачу номера. Правовые гипотезы PR #16 не проверялись
как юридическое заключение.

## Сводка по категориям

### A — можно взять как есть (подтвердить на данных)

- Email (обычный, JSON)
- Пол — только явное заявление
- Возраст, дата рождения — прямые упоминания
- Паспорт — полный, контекст + форма
- СНИЛС — формат + checksum
- Карта — формат + Luhn
- 5 из 7 подпунктов спецфлага

### B — нужна дополнительная логика

- `FULL_NAME`, `FIRST_NAME`, `LAST_NAME`, `PATRONYMIC` — адаптер разбора `PERSON`
- Телефон — подавление модельного FP, приоритет regex
- Точный адрес — структура + разведение с городом
- Пол из ФИО — отдельно, с ограничениями
- Нормализация возраста/ДР — при пересчёте
- Город — подавление `PERSON` на местоимениях
- Организация — склейка span (ООО/АО/ИП)
- Должность — zero-shot + словарь
- Родство — извлечение (словарь + модель); линковка — после #21
- ИНН — merge-правило против `PHONE`
- Части паспорта — slot-filling (вопрос 5)
- `intimate life`, `conviction` — модель/дообучение

### C — не реализуемо в текущем подходе/данных (до соответствующих задач)

- Линковка родственника и перенос атрибутов — **после [#21](https://github.com/TanellD/session-pii-detector/issues/21)**
- Линковка людей в `two_people` / `correction` — **после #21**
- Отзыв факта, накопление риска — после #21 / отдельная задача
- Сессионный F2, задержка в сообщениях — не измерены (после #11)

## Что таблица намеренно **не** утверждает

- Один TP ≠ готовность класса.
- `SPECIAL_CATEGORY` — упоминание сигнала, не юридический вывод.
- Checksum/Luhn/формат не подтверждают реальность или выдачу номера.
- `task12-smoke-v2` — диагностический набор после аудита покрытия, не blind test.
- v1/v2 не сравниваются как улучшение модели (изменены данные, зависимости,
  границы замера combined).
- Правовые гипотезы PR #16 не проверялись как юридическое заключение.
- Итог #12: ограничения покрытия измерены, готовность MVP — нет.

## Покрытие адаптера после реализации

Адаптер — единый преобразователь detector-output в mention-контракт. Он не меняет
решение о готовности модели и не доказывает качество независимым набором.

| Группа | Статус адаптера | Реализованная логика | Ограничение |
|---|---|---|---|
| EMAIL, SNILS, INN, CARD, PASSPORT, PHONE | Поддержано диагностически | Regex-упоминания сохраняют исходные границы и маппинг в project type | Не подтверждает выдачу документа или владельца |
| AGE, DATE_OF_BIRTH, GENDER, CITY, ADDRESS, OCCUPATION, RELATIONSHIP, SPECIAL_CATEGORY | Проходят через GLiNER-мapping | Label → project type по config | Низкая уверенность не отменяется адаптером; нормализация вне scope |
| FULL_NAME и части ФИО | Дополнительная логика подготовлена | Разбор 3-компонентного и контекстного PERSON-span | Не доказана устойчивость вне синтетики |
| Организация | Дополнительная логика подготовлена | Слияние span при маркере ООО/АО/ИП | Границы зависят от контекста и ещё не подтверждены данными |
| INN / PHONE, вложенные и дублирующие span | Конфликты разрешаются явным priority-правилом | INN при checksum приоритетнее перекрывающего PHONE | Не изменяет оценку baseline и не присваивает владельца |
| Линковка, отзыв факта, сессионный алерт | Не поддержано | Нет истории и нет NER всей истории | После #21 / отдельного протокола |

Подробности: [контракт упоминания](mention-contract.md), [архитектура адаптера](adapter-design.md),
[покрытие адаптера](adapter-coverage.md) и [правила конфликтов](conflicts-and-nesting.md).
