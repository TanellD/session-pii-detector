# Правильный спан профессии может не попасть в статистическую группу

- Дата: 2026-11-20.
- Автор: команда проекта.
- Связано: [сто синтетических сессий Gemma](../experiments/2026-11-19-annotation-100-gemma.md).

## Что увидели

В семействе `employment` сущность «бухгалтером» выделяется правильно, но оценщик возвращает `occupation.status=unmapped`. Используется точный проверяемый словарь соответствий, а этой словоформы в нём нет. Поэтому сочетание профессии и организации остаётся без численной оценки, с сохраняемой пометкой недостатка статистики.

## Доказательство

Локальный авторский эталон: кейс `synthetic-041` в `data/experiments/annotation-100-2026-11-19/gold-assessments.json`. Проверка без API:

```powershell
python -X utf8 -c "import json,pathlib; d=json.loads(pathlib.Path('data/experiments/annotation-100-2026-11-19/gold-assessments.json').read_text(encoding='utf-8')); print(next(c['assessment']['people'] for c in d['checks'] if c['session_id']=='synthetic-041'))"
```

Путь `people.p1.occupation` содержит `mapping_method=exact_reviewable_alias`, `status=unmapped` и `possible_codes=[]`. Оценка остаётся неизвестной, а не превращается в произвольное число кандидатов.

## Что это значит для проекта

Совпадение модели и авторского эталона по алерту не доказывает полноту статистического оценщика: оба проходят через один обработчик. Исходный спан надо сохранять как написан; для расчёта требуется отдельное проверенное сопоставление словоформ с ОКЗ. Такие изменения надо проверять на отдельном наборе численных примеров с независимо заданными ожиданиями. Словарь, старые флаги, эталон и промпт текущего запуска здесь не меняются.
