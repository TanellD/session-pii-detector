# Полные адреса терялись после успешного regex из-за точек в сокращениях

- Дата: 2026-11-25.
- Связано: [сравнение ревизии адаптера](../experiments/2026-11-25-adapter-revision.md).

## Что увидели

`predict_address_chains()` находит полную синтетическую адресную цепочку, но исходный `extract()` возвращает пустой результат. В `has_address_keyword()` проверяется принадлежность маркеров `ул`, `д`, `кв` к `lower.split()`. Реальные токены `ул.`, `д.`, `кв.` не совпадают; окно контекста не помогает, если содержит те же сокращения.

## Доказательство

```powershell
.\.venv-gliner\Scripts\python.exe -X utf8 -c "from benchmarks.pii_smoke.regex_detector import predict_address_chains; from benchmarks.adapter.adapter import extract; s='Адрес: г. Пробоград, ул. Макетная, д. 8, кв. 4.'; print(predict_address_chains(s)); print(extract(s))"
.\.venv-gliner\Scripts\python.exe -X utf8 tools/evaluate_adapter_revision.py
```

Первая команда показывает найденный regex ADDRESS и его потерю в исходном адаптере. Вторая сравнивает отдельную ревизию, восстанавливающую только полные адресные цепочки, с неизменённым baseline.

## Что это значит для проекта

До смены весов нужно проверять весь путь от модельного или regex-кандидата до сервисного спана. Отсутствие ADDRESS в финальном результате не доказывало его отсутствия на этапе поиска. Новая обёртка сохраняет полные цепочки и не переключает активный сервис автоматически.
