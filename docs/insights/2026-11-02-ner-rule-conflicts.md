# Контрольная сумма и NER требуют разных проверок

- Дата: 02.11.2026.
- Автор: `Kopylov-Andrey`.
- Связано: #12, [CPU-эксперимент](../experiments/2026-11-02-gliner-cpu.md).

## Что увидели
GLiNER дал PHONE поверх диагностического ИНН; слияние по одному типу оставило
оба сигнала. Повторное суммирование такого фрагмента способно создать ложный алерт.

## Доказательство
Случай `inn` в `runs/task12-smoke-v2/combined.json`: на одном фрагменте
`000000123411` правила дали INN, а GLiNER — PHONE. В combined по всему набору:
точные TP/FP/FN = 25/11/7, медиана CPU 252.789 ms, p95 286.495 ms.
Числа и все расхождения воспроизводятся из сохранённого прогона:

```powershell
.\.venv-task12-locked\Scripts\python.exe -m benchmarks.pii_smoke.report --input runs/task12-smoke-v2
```

Установка и новый запуск описаны в [README](../../benchmarks/pii_smoke/README.md).
Это диагностика извлечения на коротких синтетических фразах, не сессионный F2.

## Что это значит для проекта
Нужны нормализация и конфликты между типами, а не только удаление дублей внутри
типа. Контрольная сумма подтверждает формат, не выдачу номера. Score модели не
является вероятностью правонарушения. Не складывать их в один показатель.
