# Извлечение сущностей не проверяет сессионный детектор

- Дата: 2026-11-04
- Автор: не указан
- Связано: PR #20, задача #12

## Что увидели

В PR проверяется извлечение сущностей из отдельных синтетических фраз.
Общий тип PERSON не разделяет полное ФИО и части имени, а объединение
regex и GLiNER сохраняет межтиповые конфликты. Линковка людей, отзыв
фактов и накопление риска описаны в draft API, но не реализованы.

## Доказательство

Просмотренная версия PR: `55ba78f874cc622c9000460c042b30e50d66ca3e`.
[Протокол и анализ ошибок](https://github.com/TanellD/session-pii-detector/blob/55ba78f874cc622c9000460c042b30e50d66ca3e/docs/experiments/2026-11-02-gliner-cpu.md)
описывают конфликт INN/PHONE и ошибки семантических классов.
[Границы результата](https://github.com/TanellD/session-pii-detector/blob/55ba78f874cc622c9000460c042b30e50d66ca3e/docs/project/detector-research-summary.md)
явно исключают реализацию сервиса и измерение сессионного качества.
В рамках обзора эксперимент повторно не запускался.

## Что это значит для проекта

Результат можно обсуждать как исследовательский baseline. Выбор детектора
для MVP требует независимых примеров и сравнения кандидатов; качество
линковки и момента срабатывания нужно проверять отдельно. JSON-примеры
контракта сами по себе не подтверждают работу сессионного сервиса.

## Дополнение: сопоставление с issue

[Issue #12](https://github.com/TanellD/session-pii-detector/issues/12)
требует обзор, критерии сравнения, короткую CPU-проверку, draft API,
инсайт и proposed ADR. Эти артефакты присутствуют. Отсутствие реализации
сессионного сервиса и измеренного сравнения всех кандидатов не является
невыполнением этого чек-листа. Пригодность baseline для русского подтверждена
только в пределах диагностических примеров; совместимость с внутренним
API заказчика остаётся непроверенной.

Есть расхождение текста и проверки ролей:
[контракт](https://github.com/TanellD/session-pii-detector/blob/55ba78f874cc622c9000460c042b30e50d66ca3e/docs/api/session-api.md)
в разделе «Роли» связывает неполное покрытие с ожиданием содержательного
анализа assistant/tool, тогда как
[валидатор](https://github.com/TanellD/session-pii-detector/blob/55ba78f874cc622c9000460c042b30e50d66ca3e/tools/validate_api_examples.py)
в validate_pair требует неполное покрытие для любого not_in_scope.
По тому же валидатору все assistant/tool имеют not_in_scope. Значит,
обычный полный диалог лишается полного покрытия после ответа assistant.
Нужно определить область покрытия и согласовать текст с проверкой.

«По сути бесконечная» сессия из issue и удаление состояния по TTL из
draft API требуют согласования семантики, но сами по себе не доказывают
противоречия: TTL может относиться к неактивности. Нельзя представлять
это как уже согласованное ограничение. Аналогично исторический alert
после исправления — явно обозначенное предложение, не ошибка реализации.
