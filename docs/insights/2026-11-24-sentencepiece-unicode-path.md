# SentencePiece не открывает абсолютный путь с кириллицей на Windows

- Дата: 2026-11-24.
- Автор: команда проекта.
- Связано: подготовка локальной GLiNER в `benchmarks/pii_smoke/prepare.py`.

## Что увидели

После проверки хеша весов первая реальная загрузка GLiNER завершилась
`OSError` при открытии `backbone/spm.model`. Файл существовал, его хеш
совпадал с manifest. Сбой происходил в нативном `SentencePieceProcessor.LoadFromFile`
для абсолютного пути, содержащего имя пользователя с кириллицей.
Загрузка того же словаря через относительный ASCII-путь `./spm.model` работала.

## Доказательство

Подготовка теперь конвертирует исходный SentencePiece-словарь в
`tokenizer.json` отдельным процессом с cwd в backbone. Последующая стандартная
загрузка AutoTokenizer использует сохранённый fast tokenizer по абсолютному
Unicode-пути. Исходный `spm.model` и веса не изменяются. Новые файлы включаются
в manifest с хешами. Работающий процесс сервиса не меняет cwd.

Проверка идентичности ID токенов исходной стандартной fast-конвертации и
загрузки сохранённого tokenizer по абсолютному пути, без сети:

```powershell
.\.venv-gliner\Scripts\python.exe -X utf8 -m unittest discover -s tests -p 'test_prepared_gliner_tokenizer.py'
```

## Что это значит для проекта

Одной установки пакетов и скачивания весов недостаточно для проверки
работоспособности: нужен реальный запуск из пользовательского пути.
Используется тот же fast tokenizer, который AutoTokenizer выбирает по
умолчанию; это обход файловой ошибки, а не изменение checkpoint или порога.
Ограничения стандартной fast-конвертации, включая byte fallback, сохраняются.
