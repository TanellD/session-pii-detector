## Что увидели

Рабочая разметка согласована внутри текущей версии по базовым классам и качественным правилам, но ещё не образует единый готовый контур с прежним API, smoke-данными и сессионными метриками.

| Важность | Расхождение | Последствие и следующий шаг |
|---|---|---|
| Высокая | `annotation_contract.assess` выдаёт точный `first_alert` и снимает вычислительную неуверенность после достаточного алерта, даже если предыдущие префиксы имели `insufficient_data`. Протокол метрик требует `unknown`, если неизвестен первый момент. | Наличие алерта и определённость его первого момента нужно разделить. Либо неподдержанные численные ветки явно исключаются из данной версии политики, либо для timely-оценки сохраняется неизвестность первого момента. Самостоятельно выбирать одно из этих решений нельзя. |
| Высокая | `to_facts` не получает тип жилья/число квартир из адресного оценщика. Отдельная адресная форма обогащает факты, JSON-аннотация — нет. | Одна часть имени + квартира даёт неизвестный вердикт через JSON и численный алерт через обогащённые факты. Нужен единый этап обогащения с версией справочников и сохранённым результатом. Автоматическую передачу всех адресов внешнему сервису нельзя скрывать в импорт. |
| Высокая | Старый smoke извлекает `PERSON` единым спаном, новая разметка — отдельные `first_name`, `last_name`, `patronymic`. В старом наборе есть возраст, дата рождения, родство, специальные категории, отсутствующие в новой схеме. | Старые exact-match результаты нельзя сравнивать с новой разметкой без версии таксономии, адаптера и явно указанного покрытия. Простого переименования `PERSON` недостаточно. |
| Высокая | Старые regex отбрасывают СНИЛС/ИНН/карты с неверной контрольной суммой. Новая инструкция выделяет полное явно названное значение без проверки действительности. | Это разные определения извлекаемого положительного примера. Для новой версии проверка суммы должна быть отдельной диагностикой либо фильтр и эталон должны быть явно согласованы. Старые результаты остаются результатами старого протокола. |
| Средняя | Draft API использует `red_marker/two_orange/score`, `FULL_NAME`, а также неполное покрытие при любом `person_id=null`. Новый контракт — `red_rule/combination_rule/candidate_count_rule`, без `fio`-спана; неизвестная принадлежность сама по себе не включает неуверенность вердикта. | Нужны версия API/адаптер, согласование покрытия и вердикта. Draft не является готовым контрактом новой разметки. Нельзя механически переносить `candidate_count` в `risk_score`: меньшее число кандидатов означает более сильное сужение. |
| Средняя | Сохранённые локальные манифесты исходного и уточнённого пилота не совпадают с текущими хешами политики и части инструкций. | Это исторические запуски. Сохранить их и провести новую версионированную оценку; повторный расчёт по старой разметке не называть новым независимым LLM-проходом. |
| Низкая | `metrics-annotation-requirements.md` и `metrics-open-questions.md` всё ещё называют инструкцию несоставленной. Отчёт пилота говорит, что метрики не определены, хотя определения есть в `docs/kb/metrics.md`. | Обновить навигационные статусы: инструкция MVP есть, определения метрик есть; согласование полного протокола и реализация сессионного оценщика ещё не завершены. |

## Доказательство

Команда `python -X utf8 tools/audit_annotation_consistency.py` воспроизводит синтетический случай `pair_then_email`: ранние сообщения неопределённы, позднее сочетание получает `first_alert`, а флаг неуверенности сбрасывается. Эта же команда сравнивает минимальную аннотацию квартиры с обогащёнными адресными фактами и проверяет хеши сохранённых локальных манифестов. Исходные персональные значения из локальных данных не выводятся.

Остальные основания: `docs/kb/metrics.md`, `docs/api/session-api.md` и его JSON Schema, `benchmarks/pii_smoke/config.json`, `dataset.py`, `regex_detector.py`, `docs/data/schema.md` и `annotation-class-fields.md`.

## Что согласовано и что это значит для проекта

Порог с включённой границей, разделение людей, отсутствие отдельного ФИО-спана, сохранение старых спанов и исторического алерта соответствуют текущей инструкции. Локальный реальный исследовательский кеш отделён от синтетических тестовых данных и игнорируется Git; старые частоты не используются как подтверждённые частоты всего населения. Временные данные разных лет и средние жилья обозначены как приближения — это ограничение, а не скрытое равенство генеральных совокупностей.

Пилот не даёт независимой оценки качества: сценарии, аннотации и ожидания получены в одном диалоге. Прохождение тестов проверяет реализацию сценариев, не F2 детектора. Реализация сессионных F2-timely/F2-session, FP0 и протокола unknown пока отсутствует; имеющийся smoke-оценщик проверяет извлечение. Карточка датасета и разбиения также остаются незаполненными.

Для пилота можно продолжать проверку спанов и качественных правил. Перед сравнением моделей нужно согласовать первый момент при ранней неопределённости, подключить общий адресный этап, зафиксировать таксономию и независимый эталон. Правила и принятые ADR в ходе аудита не менялись.
