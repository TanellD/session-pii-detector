# Пересчёт алертов по порядку не исключает будущий контекст разметчика

- Дата: 2026-11-19.
- Связано: [последовательный пилот](../experiments/2026-11-19-user-only-sequential-pilot.md), [предыдущий офлайн-прогон](../experiments/2026-11-19-ten-session-model-comparison.md).

## Что увидели

В офлайн-прогоне модель получала весь диалог. Даже если обработчик потом перебирает сообщения по порядку, принадлежность ранней сущности могла быть выбрана с учётом позднего раскрытия владельца. Поэтому совпадение первого алерта на итоговой разметке не доказывает правильное поведение на потоке. Это ограничение протокола, а не установленное доказательство использования будущего конкретной моделью.

## Доказательство

В новом сценарии `user-04` владелец почты неизвестен на первом шаге и раскрывается позже. Политика MVP оставляет первый спан с `null`. Последовательный runner отправляет только доступный префикс и замораживает ранние сущности. Команда `tools/audit_sequential_annotation.py` из отчёта проверяет сохранённые API-запросы и неизменность ранних спанов, а не только декларацию режима.

## Что это значит для проекта

Следует отдельно указывать офлайн-разметку всей сессии и последовательную разметку. Для проверки онлайн-момента алерта недостаточно запретить будущее словами в промпте — будущих сообщений физически не должно быть в запросе. Авторский эталон также нужно проверять по префиксам. Вариант корпуса только из пользовательских реплик требует своего эталона: скрытые ответы помощника не используются для определения владельца.
