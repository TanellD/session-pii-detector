# Эксперимент: реальные выходы NER → Gemma → риск

- Дата: 2026-11-25, Москва.
- Статус: запущен, результаты обновляются в live-отчёте.
- Гипотеза: качество Gemma на эталонных спанах выше, чем качество полного пайплайна с ошибками реального извлечения.

## Настройка

- Данные: фиксированный синтетический `data/experiments/random-linker-250-2026-11-24/snapshot.json`, совпадает с предыдущими оценками линкеров.
- NER: сохранённые реальные выходы адаптера GLiNER + regex из `data/experiments/random-linker-250-gliner-2026-11-24`. Проверяются совпадение текстов, конфигурации и манифеста подготовленных весов. Выходы не заменяются эталонными и не исправляются по разметке.
- GLiNER: `benchmarks/pii_smoke/config.json`, подготовленные веса `outputs/gliner-prepared`; точные хеши — в `manifest.json → detector_identity`.
- Линкер: текущий API `Gemma-4-31B-IT`, `configs/linker-gemma-baseline.json`, исходный промпт API baseline. Локальное уточнение промпта Colab не используется.
- Риск: `configs/runtime-risk-policy.json` без подбора весов под этот прогон.
- Основа: `2172a364f5259ad7bcfd0066caba8a8004fac046` плюс незакоммиченные изменения; хеши файлов и копии конфигов сохраняются рядом с результатами.
- Инференс Gemma удалённый. Латентность NER взята из исходного CPU-замера; новый прогон воспроизводит сохранённые спаны и не повторяет вычисление GLiNER. Время текущего пайплайна включает живой LLM API, но не новый NER и не HTTP-обработчик сервиса. Это не измерение RPS.

## Команды

Из корня worktree:

```powershell
.\.venv-gliner\Scripts\python.exe -X utf8 -u tools/evaluate_gemma_linker.py --config configs/linker-gemma-baseline.json --ner-recordings data/experiments/random-linker-250-gliner-2026-11-24 --output data/experiments/gemma-real-ner-250-2026-11-25/results --all-sessions --env-file '../../.env'
```

Продолжение остановленного процесса — та же команда с `--resume`. Одновременно два оценщика в один каталог не запускаются. Невалидные спаны и ответы сохраняются как ошибки; они не превращаются в отрицательные сессии.

Все числовые результаты пересчитываются без API и весов:

```powershell
.\.venv-gliner\Scripts\python.exe -X utf8 tools/evaluate_gemma_linker.py --output data/experiments/gemma-real-ner-250-2026-11-25/results --report-only
```

Live-документ: `data/experiments/gemma-real-ner-250-2026-11-25/live-progress.md`. Наблюдатель без API:

```powershell
.\.venv-gliner\Scripts\python.exe -X utf8 tools/watch_gemma_linker.py --run data/experiments/gemma-real-ner-250-2026-11-25
```

## Результаты и знаменатели

Финальные значения ещё не получены. В `results/summary.json` сохраняются:

- Размер выбранного среза, завершённые сессии и неуспешные попытки с номером сообщения и причиной.
- Извлечение: exact type-aware Precision/Recall/F2 и разрезы по типам. Сырой выход детектора оценивается на всём срезе; выход после фильтров — на завершённых сессиях с указанием покрытия.
- Линковка: pairwise Precision/Recall/F1 только на точных совпадениях спанов и типов. Доля сопоставленных эталонных упоминаний указана отдельно. Пропуски и лишние упоминания относятся к ошибкам извлечения; эта метрика не является изолированной оценкой линкера на всех эталонных атрибутах.
- Совпадение полных групп: одновременно требует правильных упоминаний и их принадлежности; нельзя интерпретировать исключительно как качество линкера.
- Итоговые алерты: Precision/Recall/F2-session/F2-timely, исходные TP/FP/FN/TN, FP0 и смещения первого алерта. Ошибки выполнения исключены из этих метрик и публикуются отдельно; качество успешного поднабора не равно надёжности на всём срезе.
- Задержка API, текущего пайплайна с воспроизведением NER и исходного NER — раздельно, с обозначением условий замера.

Промежуточные ответы и предсказания сохраняются по сессиям и попыткам. При ошибке сохраняется также частичное предсказание; оно не оценивается как завершённая сессия.

## Анализ ошибок и ограничения

Ранее на том же NER встречались невалидные EMAIL и AGE. Текущий прогон должен показать их влияние на полный пайплайн, а не скрывать фильтрацией по эталону. Синтетические сценарии короткие и частично использованы при отладке; вывод о качестве на реальных чатах этим экспериментом не обосновывается. Для сравнения с эталонными спанами требуется одинаковый набор успешных ID с отчётом покрытия.
