# Последовательная разметка пользовательских сессий Gemma

- Дата: 2026-11-19.
- Базовый коммит: `137a3c0`; генератор, последовательный runner, аудит и отчёт добавлены вместе.
- Задача: создать разговорные пользовательские обращения и проверить разметку без будущего контекста.
- Инструкция: [шаблоны и работа с пользовательскими сообщениями](../data/user-only-synthetic-sessions.md).
- Эталон: авторская разметка текущей LLM, составлена до API-запросов; независимая проверка человеком ожидается.

## Данные

```powershell
python -X utf8 tools/build_user_only_sessions.py
```

Генератор создаёт **6 сессий, 15 пользовательских сообщений, 16 сущностей; 4 положительные и 2 отрицательные сессии**. Эти числа выводятся командой. Генератор не перезаписывает каталог; для повторения нужен новый `--output`. Значения вымышлены: `.invalid`, телефоны с нулевым кодом, нулевой номер карты. Разговорная структура приближена к обращениям в поддержку; это диагностическая синтетика, а не выборка реальных клиентов.

Исходные сессии созданы сразу без ответов чатбота. Все сообщения — от одного пользователя внутри соответствующей сессии. Эталон не использует невидимые ответы помощника. Нейтральные ID `user-01` … `user-06` не раскрывают модели название сценария.

| ID | Сценарий | Первый алерт по авторскому эталону |
|---|---|---|
| `user-01` | Чистый вопрос о настройке уведомлений | Нет |
| `user-02` | Доставка, ФИ, адрес и исправление квартиры | `m2`, сочетание |
| `user-03` | Запись, имя, отчество и личная почта | `m3`, сочетание |
| `user-04` | Почта неизвестного владельца, позднее раскрытие, ФИ и телефон | `m3`, сочетание |
| `user-05` | ФИ и явно служебные телефон/email | Нет |
| `user-06` | Вопрос о возврате, затем полный номер карты | `m2`, красное правило |

В `user-04` email из первого сообщения остаётся с `person_id=null`, когда позднее раскрывается владелец. В повторной реплике самого email нет. Изменять прежний спан нельзя. При корректной истории алерт появляется после нового личного телефона, а не ретроспективно после имени. Этот случай проверяет правило неизменности; защиту от доступа к будущему дополнительно проверяет инструмент по сохранённым запросам.

Каталог `data/experiments/user-only-sessions-2026-11-19/`:

- `sessions-for-review.md` — тексты и эталон для чтения.
- `sessions.json` — только сообщения, передаваемые модели.
- `gold.json`, `gold-assessments.json` — сущности и рассчитанные первые алерты.
- `gold-prefixes.json` — авторское состояние по каждому доступному префиксу.
- `manifest.json` — происхождение и хеш генератора.

## Протокол модели

```powershell
python -X utf8 tools/run_sequential_annotation.py --input data/experiments/user-only-sessions-2026-11-19/sessions.json --output data/experiments/radeon/2026-11-19-user-only-gemma-sequential-01 --model Gemma-4-31B-IT --timeout 120 --max-tokens 4000 --delay 3
```

Режим `sequential_user_only_v1`, транспорт `annotation-quotes-v1`, конечная схема `annotation-mvp-v2`, политика `2026-11-18-working-v2`. Инструкции включают общий промпт, таблицу классов, машиночитаемый контекст политики и правила последовательного режима. Параметры: temperature=0, без streaming. Ревизия облачных весов не подтверждена. Сетевой timeout не является измеренной задержкой всей сессии.

На шаге модель получает только сообщения до текущего включительно и собственное предыдущее предсказание. Эталон, названия сценариев и будущие реплики не отправляются. Она размечает только текущее сообщение; попытка вернуть прежние сущности отклоняется. Границы вычисляются по точным цитатам, ID упоминаний назначает инструмент. Значения, типы и владельцы не исправляются автоматически.

Старые сущности и их принадлежность заморожены, предыдущие пометки неуверенности сохраняются. Обработчик добавляет вычисляемую часть флагов и рассчитывает алерты после каждого сообщения. Следующий шаг получает это модельное состояние, а не авторский эталон. Поэтому ошибка прошлого шага может повлиять на следующие шаги — это часть последовательной проверки.

При невалидном ответе или тайм-ауте текущая сессия останавливается и сохраняет полученные префиксы. Следующая сессия начинается заново. HTTP-ошибка останавливает весь прогон. Повторов и молчаливой замены результатов нет. Частичная сессия не объявляется отрицательной.

## Проверка запросов и сравнение

Первоначально команды выполняются без `--check`, для повторной проверки сохранённых результатов — с ним:

```powershell
python -X utf8 tools/audit_sequential_annotation.py --source data/experiments/user-only-sessions-2026-11-19 --run data/experiments/radeon/2026-11-19-user-only-gemma-sequential-01 --output data/experiments/user-only-sessions-2026-11-19/sequential-audit.json --check
python -X utf8 tools/compare_annotation_models.py --gold data/experiments/user-only-sessions-2026-11-19 --runs data/experiments/radeon/2026-11-19-user-only-gemma-sequential-01 --output data/experiments/user-only-sessions-2026-11-19/model-comparison.json --check
```

Аудит проверяет точное равенство пользовательского payload разрешённому префиксу, предыдущему сохранённому предсказанию и фиксированному набору полей. Для успешных шагов проверяется неизменность старых сущностей; результаты сравниваются с авторскими префиксами. Сырые запросы и ответы остаются отдельно в каталоге запуска.

Корпусное сравнение использует только полностью завершённые сессии и явно показывает покрытие. Частичные сессии видны в аудите шагов, но не превращаются в FN или TN. Извлечение — exact/type-aware, группировка — строгое совпадение со спанами с точностью до ID персон. Исходные флаги последнего ответа модели показаны отдельно от накопленных/вычисленных флагов.

В отличие от [прошлого прогона готовых сессий](2026-11-19-ten-session-model-comparison.md), здесь проверяется доступ к данным в момент каждого шага. Прежние офлайн F2-timely — совпадение моментов после разметки всей сессии, а не доказательство поведения без доступа к будущему.

## Проверки реализации

`python -X utf8 -m unittest discover -s tests` — **176 тестов прошли**. Новые проверки подтверждают отсутствие будущих сообщений в payload, неизменность старого неизвестного владельца и прежних флагов, отклонение старых спанов в новом ответе и изменённого списка сообщений. Проверены также остановка текущей сессии после тайм-аута с пустым состоянием следующей и остановка всего запуска на HTTP 429. Это проверки протокола; они не заменяют аудит фактических запросов и независимую проверку эталона.

## Результаты

Числа воспроизводятся двумя командами `--check` выше по сохранённым запросам и ответам.

| Показатель | Результат |
|---|---|
| API-запросов / валидных шагов | 15 / 15 |
| Полностью завершённых сессий | 6 / 6 |
| Тайм-аутов и невалидных ответов | 0 |
| Извлечение: TP / FP / FN | 16 / 0 / 0 |
| Все спаны и владельцы совпали с авторским эталоном | 6 / 6 сессий |
| F2-session: TP / FP / FN / TN | 4 / 0 / 0 / 2 |
| F2-timely: TP / FP / FN / TN | 4 / 0 / 0 / 2 |
| Первый алерт совпал на каждом проверенном префиксе | 15 / 15 шагов |
| Исходные флаги последнего ответа совпали с эталоном | 6 / 6 сессий |
| Флаги после обработчика совпали | 6 / 6 сессий |

Precision, Recall и F2 извлечения, F2-session и F2-timely равны 1 на этом наборе. Смещения первого алерта положительных сессий — `[0, 0, 0, 0]`. FP0 по уверенно отрицательному подмножеству — 0/1; второй отрицательный пример имеет историческую пометку нехватки статистики и остаётся в F2-session. Эти знаменатели явно показаны в JSON-сравнении.

В `user-04` исходная почта осталась без владельца, после второго сообщения алерта не было, после третьего сработало сочетание ФИ и нового телефона. В `user-02` исправление квартиры добавлено новым спаном, исторический первый алерт остался на втором сообщении. В `user-05` оба служебных контакта сохранились с `null`. В `user-06` полный номер карты дал красный алерт на втором сообщении.

Аудит проверил все сохранённые запросы: пользовательский payload содержит только разрешённый префикс и собственное прежнее предсказание, системный промпт совпадает с зафиксированным хешем, дополнительных сообщений/полей с будущим или эталоном нет. Старые сущности всех успешных шагов совпали побайтно как структуры JSON. Персоны, значения и типы исходных ответов не исправлялись; инструмент назначал ID упоминаниям и сохранял вычисляемые флаги.

Отсутствие тайм-аутов в этом прогоне не доказывает, что последовательный режим быстрее: набор и состав инструкций отличаются от прошлого, условий для такого сравнения не фиксировали. Исходные флаги последнего ответа также не являются независимой проверкой способности модели считать статистику: она получала накопленные пометки обработчика в предыдущем состоянии.

Итоговые локальные файлы: `model-comparison.md` для чтения, `model-comparison.json` со счётчиками и `sequential-audit.json` с проверкой каждого шага. Данные и ответы API не коммитятся. Следующий шаг — проверка пользователем авторского эталона, затем расширение набора на более неоднозначные формулировки и разных явно указанных людей. Нулевые ошибки на короткой синтетике не означают готовность массовой разметки или независимую оценку качества модели.
