# Проверка сборки HTTP-каркаса в Docker

- Дата / автор: 2026-11-20, команда проекта.
- Связано: [описание API и интеграции](../api/service-scaffold.md), PR #44.
- Гипотеза: отдельные интерфейсы компонентов позволят собирать сервис и проверять состояние/правила до появления настоящих NER, regexp и линкера.

## Настройка

- Базовый коммит: `022bf62`; исходный код и документация каркаса поставляются вместе с отчётом.
- Данные: только синтетические строки из `tests/service/test_runtime.py` и `tools/smoke_service.py`; корпуса и `.env` не загружаются.
- Конфиг: текущая `annotation-estimator-policy.json`, `Calculator(policy_only=True)`; компоненты по умолчанию — заглушки. Для интеграционных тестов подставляются небольшие тестовые компоненты.
- Стек: FastAPI/Uvicorn, фиксированные версии в `requirements-service.lock.txt`; Python 3.12 в Linux-контейнере Docker Desktop. GPU и модели не используются.
- Один процесс Uvicorn; состояние ограничено памятью процесса. Эксплуатационные лимиты заданы в Compose и описаны в руководстве.

## Команды и результаты

`.venv-service\Scripts\python.exe -X utf8 -m unittest discover -s tests/service -v` — **15 тестов прошли**. Проверены межсообщенческое сочетание, красный маркер с неизвестным владельцем, частичное покрытие, различение неизвестного владельца и неуверенности, сохранение истории пометок, Unicode code points, дедупликация и отклонение перекрытий, атомарность ошибок, CAS, точный/конкурентный retry, reset/epoch, изоляция сессий, TTL и лимиты. Типы сущностей сверены с конфигом классов.

`python -X utf8 -m unittest discover -s tests` — **184 исследовательских теста прошли** после совместимого изменения импортов калькулятора и валидатора.

Локальный Uvicorn запущен на `127.0.0.1:8017`; `.venv-service\Scripts\python.exe -X utf8 tools/smoke_service.py --base-url http://127.0.0.1:8017` вернул `status=ok`, точный retry и ожидаемое неполное покрытие заглушек.

Docker Desktop первоначально не был запущен. После запуска установленного приложения удалось собрать образ и проверить контейнер:

```powershell
$env:PII_HOST_PORT='8018'
docker-compose -p session-pii-scaffold-smoke up --build -d
.venv-service\Scripts\python.exe -X utf8 tools/smoke_service.py --base-url http://127.0.0.1:8018
docker-compose -p session-pii-scaffold-smoke ps
docker-compose -p session-pii-scaffold-smoke exec -T pii-service python -c "import os,pathlib; print({'uid':os.getuid(),'env_in_image':pathlib.Path('/app/.env').exists(),'data_in_image':pathlib.Path('/app/data').exists()})"
```

Результат: сборка успешна, контейнер `healthy`, HTTP smoke успешен. Процесс работает под UID **10001**; `/app/.env` и `/app/data` отсутствуют. Поведение заглушек совпадает с локальным запуском. Проверялся Compose с файловой системой только для чтения и опубликованным loopback-портом. Тестовый Compose-проект и локальный сервер останавливаются после проверки; образ остаётся для дальнейшего запуска.

Та же последовательность сборки, healthcheck и HTTP smoke добавлена отдельным заданием в CI. Локальная проверка не выдаётся за результат ещё не запущенного GitHub Actions.

## Анализ ограничений

Это проверка интеграции и упаковки, не замер качества распознавания. Настоящие NER, regexp и линкер ещё не подключены; метрики модели, latency-нагрузка, общий storage, аутентификация и адресное обогащение этим прогоном не проверяются. Неизвестные зависимости статистики остаются неизвестными. Не утверждаются промышленная готовность и совместимость с историческим API draft v0.1.

## Следующий шаг

Подключить реализации через `create_app` по контрактам `Detector`/`Linker`, затем повторить интеграционные проверки и отдельный размеченный benchmark. Сохранить явную неполноту стадий до окончания интеграции; не заменять её фиктивным успешным ответом.
