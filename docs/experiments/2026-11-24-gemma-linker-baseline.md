# Эксперимент: Gemma как baseline назначения владельцев

- Дата / автор: 2026-11-24; команда проекта.
- Задача: использовать выбранную пользователем `Gemma-4-31B-IT` вместо
  случайного назначения владельцев для LLM-бейзлайна.
- Гипотеза: контекст сообщения, карточки людей и ограниченное окно прошлых
  сообщений достаточны для первого содержательного baseline; правильность
  принадлежности оценивается отдельно от NER.

## Настройка

- Базовый коммит: `2172a36`; код, тесты и документация поставляются вместе.
- Источник: фиксированный синтетический снимок
  `data/experiments/random-linker-250-2026-11-24/snapshot.json`.
  Авторский эталон, без независимой проверки человеком.
- Выбрано по первому случаю разных людей, общего личного телефона с личной
  почтой, общего адреса, неизвестных контактов, позднего уточнения с повтором
  атрибута и служебных контактов. Это направленный отладочный пилот.
- Извлечение: эталонные спаны. Внешняя модель получает текущий текст,
  кандидатов, **предсказанные** карточки владельцев и доступный прошлый контекст.
  Правильные владельцы, family, ожидаемые алерты и будущие сообщения ей не передаются.
- Модель: alias `Gemma-4-31B-IT`, Radeon Chat Completions API. В ответах —
  `self-dploy/Gemma-4-31B-IT`; revision checkpoint и оборудование не раскрыты.
- Конфиг: `configs/linker-gemma-baseline.json`; температура и схема фиксированы.
  Риск: `runtime-risk-v2`; веса и эталонная разметка не подгонялись.
- Машина клиента: локальная Windows x64, Python из `.venv-gliner`.
  Инференс LLM выполняется у провайдера, не на локальном CPU.

## Протокол и изменения

`GemmaLinker` назначает владельцев всем кандидатам одним запросом.
Новые `new:N` преобразуются кодом в локальные ID; проверяются существующие
ID, полный набор кандидатов, уникальность владельцев и служебные контакты.
Упоминания и типы модель изменить не может. Неполный ответ и ошибка API
не изменяют состояние сервиса. Линкер не хранит межсессионную память.

Первый пилот `gemma-linker-pilot-2026-11-24` использовал только текущее
сообщение и известные факты. В `synthetic-1000-0021` общий телефон был
связан правильно, но почта «только моя» оказалась у нового человека:
карточки имён не сохраняли, кто из двух представлялся как говорящий.

В `gemma-owner-linker-v2` обработчик передаёт ограниченное окно прошлых
сообщений. Оно хранится внутри сессии, коммитится вместе с результатом,
очищается при reset и не выводится в GET. Сообщения без кандидатов также
входят в окно. Заглушки и старый интерфейс линкера продолжают работать.
Второй пилот — `gemma-linker-context-pilot-2026-11-24`.

Это последовательная отладка по тем же случаям. Исправление контекста
и повторный результат не являются независимой оценкой улучшения модели.
Промпты и исходные ответы обоих запусков сохранены, предыдущие результаты
не переписывались под новые решения модели.

## Воспроизведение

Все числа таблицы и разбор случаев воспроизводятся без внешнего API:

```powershell
.\.venv-gliner\Scripts\python.exe -X utf8 tools/evaluate_gemma_linker.py --output data/experiments/gemma-linker-pilot-2026-11-24 --report-only
.\.venv-gliner\Scripts\python.exe -X utf8 tools/evaluate_gemma_linker.py --output data/experiments/gemma-linker-context-pilot-2026-11-24 --report-only
```

Новый живой пилот следует сохранять в новый каталог:

```powershell
.\.venv-gliner\Scripts\python.exe -X utf8 tools/evaluate_gemma_linker.py --output data/experiments/gemma-linker-next --env-file '..\..\.env'
```

Полный срез запускается через `--all-sessions`. Эта работа пока не выполнялась:
текущий результат относится к пилоту. Возобновление — `--resume`; успешные
сессии не вызывают API повторно. На ошибке транспорта запуск останавливается
без скрытых повторов. Старые попытки сохраняются.

Pairwise рассчитан по [протоколу](../kb/metrics.md) на конечном состоянии:
в каждом пилоте оцениваются 16 упоминаний с известным эталонным владельцем,

Скорость указана по успешным вызовам малого последовательного пилота.
Это не максимальный RPS и не нагрузочный тест; отличие времени между
пилотами не доказывает ускорение от добавленного контекста. Внутренний
бюджет сервиса и внешний LLM round-trip различаются по принятой методике.

## Анализ ошибок

- Без текста истории потерялось соответствие говорящего одному из двух
  людей. Добавление ограниченного контекста исправило этот конкретный случай.
  [Подробная заметка](../insights/2026-11-24-linker-speaker-context.md).
- С контекстом остаётся один FP алерта: `synthetic-1000-0046`. Оба контакта
  правильно оставлены без владельца. Runtime складывает их веса выше порога
  неизвестной группы; по эталонной политике алерт не нужен. Это известное
  расхождение риска, а не ошибка Gemma-линера.
- Ошибки NER этим пилотом не измеряются. Найденные ранее невалидные EMAIL/AGE
  от GLiNER остаются отдельной задачей адаптера.
- Ограниченный контекст может потерять давнюю связь или роль говорящего.
  Малый пилот не проверяет длинные диалоги, противоречия, устойчивость к
  переформулировкам и качество на распределении реального чат-бота.

## Проверки и следующий шаг

```powershell
.\.venv-gliner\Scripts\python.exe -X utf8 -m unittest discover -s tests/service -p 'test_*.py'
```

Тестами покрыты контракт ответа, общие и неизвестные владельцы, служебные
контакты, границы контекста, отсутствие будущих сообщений, retry без нового
вызова, reset, изоляция сессий и отсутствие коммита на ошибке модели.

Gemma подключена как явно выбираемый LLM-бейзлайн. Для содержательного
сравнения со случайным линкером нужен полный срез с теми же спанами и
отдельный независимый набор после отладки. Для быстрого чат-бота необходимо
отдельно измерить и сократить внешнюю задержку, а не выводить RPS из этого пилота.
Контракт и команды сервиса — [в инструкции](../api/gemma-linker-baseline.md).
