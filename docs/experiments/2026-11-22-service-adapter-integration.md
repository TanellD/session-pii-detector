# Интеграция адаптера Олеси с сессионным сервисом

- Дата / автор: 2026-11-22, команда проекта.
- Гипотеза: общий адаптер можно подключить один раз на новое сообщение, сохраняя происхождение, уникальность упоминаний и разделение людей.
- Код: рабочие изменения поверх 07f0aea, согласованные с main на d777cfa; воспроизводить на коммите интеграционной ветки.
- Данные: синтетические сервисные тесты и локальный session-alerts-v3, подготовленный командой миграции из PR #46. Данные остаются вне Git.
- Конфиг: runtime-risk-v2; regex-режим по умолчанию. GLiNER и настоящий линкер не используются в замере.
- Окружение: Windows, Python из .venv-service, TestClient и отдельный Uvicorn на localhost.

## Команды

```powershell
.venv-service\Scripts\python.exe -X utf8 -m unittest discover -s tests/service
python -X utf8 -m unittest discover -s tests
.venv-service\Scripts\python.exe -m uvicorn session_pii.app:app --app-dir src --host 127.0.0.1 --port 8022 --workers 1 --no-access-log
# В другом терминале:
.venv-service\Scripts\python.exe -X utf8 tools/smoke_service.py --base-url http://127.0.0.1:8022 --expect-adapter
.venv-service\Scripts\python.exe -X utf8 tools/replay_service_corpus.py --input data/session-alerts-v3/sessions.json --output data/experiments/service-adapter-integration-2026-11-22/replay.json
```

Путь к Python выбирается по расположению окружения. В изолированной рабочей копии использован ../../.venv-service/Scripts/python.exe; источник корпуса — ../pr46-finalization/data/session-alerts-v3-final/sessions.json. Для повторного прогона нужен новый выходной файл. Манифест и код подготовки корпуса описаны в docs/data/session-alerts-pilot.md.

## Результаты

Сервисная команда: 42 теста прошли. Исследовательская команда: 223 теста, один явно пропущен. Живой HTTP-smoke подтвердил regex-извлечение, точный retry, ключи сессии и красный алерт на синтетическом валидном СНИЛС. Команда replay обработала 24 сессии и 61 сообщение без ошибок; источник проверяется SHA-256, сохранённым в replay.json.

Результаты replay не являются F2 или оценкой весов: используются заглушка линкера, отсутствие эталонных владельцев на входе и отдельная runtime-политика. Качественный эталон назначается независимо по ТЗ, веса сервиса настраиваются по разметке, не наоборот. Все выводы ограничены проверенной интеграцией.

Проверены общий PERSON как жёлтый атрибут, отсутствие повторного вклада при уточнении, форматные повторы телефона, вложенные имена в организациях/контактах, адрес и география, происхождение и составные ключи упоминаний. Неоднозначное пересечение приводит к отказу без изменения состояния. Ошибка модели не маскируется переходом к regex и не отражает исходный текст в HTTP-ошибке.

## Ограничения

Локальный Docker Engine недоступен; сборка и HTTP-smoke включены в CI с --expect-adapter. Базовый образ не включает GLiNER и веса. Модельный путь проверен инъекциями синтетических выходов, без загрузки модели; это не доказательство качества GLiNER. Для полного сессионного результата требуется реальный линкер и независимая проверка нового gold.
